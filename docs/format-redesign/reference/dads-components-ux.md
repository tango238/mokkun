# DADS v2 コンポーネント UX 利用ルール抽出ノート

- 出典: デジタル庁デザインシステム（DADS）β版サイトの Markdown ダンプ `md/components/<name>/index.md`（各ページの「概要」「使い方」「アクセシビリティ」等の章）
- パスはすべて `dads-markdown/` からの相対パス
- 抽出方針: ドキュメントに書かれているルールのみを1文で記載（数値はそのまま保持）。画像の代替テキストで示された良い例・悪い例から読み取れる事項は「（図例）」と付記。
- link（リンク）コンポーネントのページはダンプに存在しないため対象外。

---

## インプットテキスト / Input Text
- 用途: 名前や電話番号など、1行以内のテキストを入力する場合（ユーザーから単一行のテキスト情報を収集するとき）。
- 使わない場面: 自由記述（複数行）はテキストエリアを使う（関連: テキストエリア、セレクトボックス、日付ピッカー）。穴埋め文章の形式には使えない。
- ルール:
  - 構成要素は入力フィールド（必須）・項目ラベル（必須）・要否ラベル・サポートテキスト・エラーテキストで、項目ラベルは必須要素である。
  - サイズは Large（高さ56px）・Medium（48px）・Small（36px）の3種で、周囲のUI密度に応じて選ぶ。
  - 入力フィールドの横幅は入力内容に相応しい長さにする（全フィールドを等幅にしない・図例）。
  - 項目ラベルとサポートテキストは垂直に積み、入力フィールドとエラーテキストも垂直に積む。
  - ラベル群とフィールド群を垂直に積むか水平に並べるかはフォームのボリュームやサイト特性で決め、読み物サイトのフォームでは多くの場合垂直に積む（垂直積みはモバイル耐性が高く多くの場合で推奨）。
  - 水平配置の場合はラベル右寄せ／左寄せ／ラベル直後配置のいずれも可で、ラベル左端や余白を揃える。
  - 要否ラベルは入力の必要性に応じて「※必須」「※任意」またはステート表示（例: 「編集不可」）を付与する。
  - 要否ラベルは「※（全角米印）」から書き始める。
  - サポートテキストには入力形式の条件や例を簡潔かつ具体的に記述し、エラーが出る前に必要十分な入力条件を提示する。
  - サポートテキストの代わりにプレースホルダーテキストを使用してはならない（原則プレースホルダー自体を使わない）。
  - エラーテキストには具体的なエラー内容および訂正方法を記述し、「入力に誤りがあります」「正しい〜を入力してください」のような曖昧な文言にしない。
  - エラーテキストの冒頭に「＊（全角アスタリスク）」を付与する。
  - 必須項目が空欄の場合も、不適切な値と同様の具体的なエラーを示す。
  - 穴埋め文章として入力欄を埋め込まず、見出し／サポートテキストに続けて項目ごとのラベル＋インプットテキストで構成する（単位のみの付随は可）。
  - 原則として入力できる文字種を限定しない。
  - 文字種を限定せざるを得ない場合は自動変換による入力支援を推奨し、変換タイミングは送信ボタン押下時または確認画面表示時とする（入力直後・フォーカスアウト時は避ける）。
  - 自動変換しない場合はエラーを表示し、表示タイミングは送信ボタン押下時または押下後が望ましい（入力直後・フォーカスアウト時のエラー表示は避ける）。
  - 自動変換した結果は確認画面等で表示し、ユーザーが承認または修正できるようにする。
  - 無効フィールド（`disabled`）を使わない。
  - 編集不可フィールド（`readonly`）は原則使わず、編集できない項目は地の文として表示する。
  - 編集不可フィールドが許容されるのは、既存システムの制約・連なるフィールドで異なるステートが混在・表示モードと編集モードが明示的に切り替わる場合に限る。
  - 編集不可フィールドを使う場合は確認画面で使用せず、DADS の編集不可フィールド（点線ボーダー、要否ラベルに「編集不可」、サポートテキストに編集できない理由）を使う。
  - 最大長の制限に `maxlength` 属性を使用しない。
  - 最大文字数の制約はサポートテキストで提示する（または十分長いテキストを受け入れる）、サーバーサイドで検証し超過時は最大文字数および超過文字数をエラーテキストで表示する。
  - コピー操作・ペースト操作を禁止しない。
  - メールアドレスを `@` の前後で分割したフィールドにしない（確認は確認メール送信で行う）。
  - 値の変更をトリガーに新しいウィンドウ／ダイアログの起動、フォーム送信・遷移、値の書き換えと同時のフォーカス移動を起こさず、ボタンやリンクの押下をトリガーにする。
  - 後続フォームの変化や、変化が起きることを事前にテキストで伝えている場合は予測できない変化とはみなされない。
  - エラーテキストを `aria-live` や `role="alert"` で通知してはいけない（静的テキスト表示で十分、強調したい場合は `aria-describedby` で紐づける）。
- 文言:
  - 要否ラベル: 「※必須」「※任意」、ステート「編集不可」。
  - サポートテキスト例: 「半角数字のみ」、「氏と名を空白で区切ってください。」、編集不可時「この項目は自動入力されたので変更できません。」
  - エラーテキスト例（良）: 「＊氏名を入力してください。」「＊氏名をカタカナで入力してください。」「＊氏（カタカナ）と名（カタカナ）を空白で区切ってください。」
  - エラーテキスト例（悪）: 「＊入力に誤りがあります。」「＊正しい氏名（カタカナ）を入力してください。」
- 出典: `md/components/input-text/index.md` — 「概要」ユースケース、「使い方」外観（コンポーネント要素／サイズ／横幅／整列）、コンテンツ（要否ラベル／サポートテキスト／エラーテキスト／穴埋め文章ではなく、項目ごとに入力する）、入力値の文字種を限定しない、「アクセシビリティ」（プレースホルダーテキストを使わない／無効フィールドを使わない／編集不可フィールドを使わない／maxlength属性を使用しない／コピー＆ペーストを無効にしない／メールアドレスを分割しない／値の変更で予測できない変化を引き起こさない／エラーテキストの読み上げに aria-live を使わない）

## テキストエリア / Textarea
- 用途: 自由記述テキストを入力する場合。
- 使わない場面: 自由入力は負荷が高いため、まず質問を分割（選択式の質問＋「その他を選んだ方だけご記入ください」等）できないか検討する。
- ルール:
  - 構成要素は入力フィールド（必須）・項目ラベル（必須）・要否ラベル・サポートテキスト・文字数カウンター・エラーテキストで、文字数カウンターは入力フィールドの下、エラーテキストはその下に左寄せで置く。
  - 質問を分解し、最低限の記述で済むようにする（オープンすぎる質問は避ける・図例）。
  - ラベルテキストは入力項目を端的に表現する（入力項目が1つで画面タイトル等で意味を明確に説明できる場合は省略可）。
  - 文字数制限がある場合はラベルに最大文字数を具体的に記述する。
  - 最大文字数がおおむね20文字を超える、または入力フィールド内でスクロールが必要な文字数以上の場合は文字数カウンターを併せて表示する。
  - 制限超過時はエラーを表示し、入力済み文字数（超過数）を示して修正しやすくする。
  - エラーが出て初めて文字数制限が分かる、またはエラーでも上限が分からない状態にしない（図例・悪い例）。
- 文言:
  - ラベル例: 「困っていることを100文字以内で教えてください」
  - エラー例: 「＊入力できる文字数を超えています。（入力文字数101文字）」
- 出典: `md/components/textarea/index.md` — 「概要」、「使い方」仕様（パーツ）、使い方（設計の原則／文字数に制限がある場合）

## セレクトボックス / Select
- 用途: 複数の選択肢を提供するフォームコントロール（選択肢が6個以上など、ある程度多い場合）。
- 使わない場面: 選択肢が5つ以下の場合はラジオボタンを推奨。あまりに長いリストは事前の質問で選択肢を減らせないか検討する。
- ルール:
  - 構成要素はセレクトボックス・項目ラベル・要否ラベル・サポートテキスト・ドロップダウンアイコン（右端の下向きシェブロン）・エラーテキスト。
  - 展開時のオプションリストは規定スタイルを持たず、OSデフォルト（標準UI）のスタイルを使う。
  - 長すぎるリストはモバイルでの使い勝手を下げるため、事前の質問で選択肢を減らせないか検討する。
  - リストが5つ以下ならラジオボタンを使う（選択肢が2つでセレクトボックスを使うのは悪い例、6個なら良い例）。
  - ラベルテキストは入力項目を端的に表現する（入力項目が1つで画面タイトル等で説明できる場合は省略可）。
- 文言: 特記なし（要否ラベルは赤文字で項目ラベルの後ろ）。
- 出典: `md/components/select/index.md` — 「概要」、「使い方」仕様（パーツ／オプションリストの実装）、使い方（設計の原則）

## チェックボックス / Checkbox
- 用途: 複数の項目の中から複数の選択肢を選ぶとき、またはひとつの選択肢のオン・オフ切り替え。
- 使わない場面: 複数の選択肢から1つしか選べない場合は必ずラジオボタンを使う。
- ルール:
  - 構成要素はチェックボックスと選択肢ラベルで、チェックボックスはテキストの左側に配置する（拡大表示利用者が見つけやすい）。
  - サイズは S・M・L がある。
  - 単一回答を求める質問（例: 「あなたは申請者本人ですか？」）にチェックボックスを使わない。
  - ラベルテキストは入力項目を端的に表現する（入力項目が1つで画面タイトル等で説明できる場合は省略可）。
- 文言: 質問文例「好きな食べ物をすべて選んでください。※必須」（複数選択可であることを「すべて選んでください」で示す・図例）。
- 出典: `md/components/checkbox/index.md` — 「概要」、「使い方」仕様（パーツ）、使い方（設計の原則）

## ラジオボタン / Radio Button
- 用途: 選択肢の中から1つだけを選択できるようにする場合。
- 使わない場面: 複数回答できる質問にはチェックボックスを使う。
- ルール:
  - 構成要素はラジオボタンと選択肢ラベルで、ラジオボタンは選択肢ラベルの左に配置する。
  - サイズは S・M・L がある。
  - ラジオボタンは選択解除できないため、任意項目で使う場合は「あてはまるものはない」のような無選択状態を意味する選択肢を設ける。
  - 選択肢が5個以下ならセレクトボックスではなくラジオボタンを使う（セレクトボックス側の規定）。
- 文言: 無選択の選択肢「あてはまるものはない」、例「はい／いいえ／どちらとも言えない」。
- 出典: `md/components/radio/index.md` — 「概要」、「使い方」仕様（パーツ）、使い方（設計の原則）; `md/components/select/index.md` — 設計の原則

## 日付ピッカー／カレンダー / Date Picker
- 用途: ユーザーに日付を入力させる幅広い場面。カレンダーはイベント開催日・宿泊期間・スケジュールなど比較的短い期間の範囲から曜日や前後を確認しながら選ぶとき。
- 使わない場面: 生年月日・履歴書の経歴年月・クレジットカード有効期限など特定可能な既知の日付ではカレンダーボタンを置かない（直接入力のみ）。`<select>` や `<input type="date">` の使用は避ける。
- ルール:
  - 入力フィールドは年・月・日の3つのテキストフィールドと項目ラベル（必須）・要否ラベル・サポートテキストで構成し、エラー時は赤いボーダーとフィールド下のエラーテキストを示す。
  - カレンダーボタンは入力フィールドの右、カレンダーパネルは入力フィールドの下に左寄せで表示する。
  - 表示タイプは Consolidated（ひとまとまり）または Separated（年月日独立）から選ぶ。
  - 要件に応じて日フィールドを省略（年月入力）または年フィールドを省略（月日入力）してよい。
  - 要否ラベルはラベルの隣に「※必須」または「※任意」と記載する。
  - サポートテキストで年が西暦であることと年月日全体の具体的な入力例を示し、プレースホルダーテキストは使わない。
  - 和暦対応の日付ピッカーは現時点で提供していない。
  - 年月日のフォーカスを自動で移動させない。
  - フォーカス時に IME の制御を行わない。
  - 全角数字が入力された場合はエラーにせず半角数字に正規化（自動訂正）する。
  - ゼロ埋めされていない数字はエラーにせずゼロ埋めに正規化する。
  - 入力フィールド・カレンダーボタン・カレンダーパネルに `disabled` を指定しない（やむを得ず無効化する場合は近くに無効である旨と表示条件をテキストで記載する）。
  - Consolidated タイプでは、キャレットが右端にあるとき `→` で次フィールドへ、左端にあるとき `←` で前フィールドへフォーカス移動を実装することを推奨する。
  - カレンダーパネルはカレンダーボタン押下によってのみ表示し、マウスオーバーやフォーカスで表示してはいけない。
  - 初めてカレンダーを開くときは「今日」を含む年月を表示する（合理的理由がある場合を除く）。
  - 入力フィールドの値をカレンダーに反映し、入力日を含む年月を表示して Selected にする。
  - カレンダーのマークアップとキーボード操作は ARIA Authoring Practices Guide（Date Picker Dialog）に準じる。
  - 文脈に応じて `autocomplete`（`bday-year`/`bday-month`/`bday-day`/`cc-exp-month`/`cc-exp-year`）を指定する。
- 文言: サポートテキスト例「西暦で記入してください。例）2021年09月01日」、要否ラベル「※必須」「※任意」。
- 出典: `md/components/date-picker/index.md` — 「概要」ユースケース、「使い方」コンポーネント要素、外観（表示タイプ／カスタマイズ／カレンダーを使用するとき）、コンテンツ（ラベル／サポートテキスト）、ふるまい（入力フィールド／キーボード操作支援／カレンダー）、「アクセシビリティ」（select要素および input type="date" の使用を避ける／autocomplete を使用する）

## ファイルアップロード／ドロップエリア / File Upload
- 用途: フォームでファイルのアップロードを受け付けるとき、ウェブアプリのファイル一覧画面でファイルを追加するとき（`<input type="file">` 相当、単体または複数、ドラッグ＆ドロップ可）。
- 使わない場面: ドロップエリアのみの構成（ファイル選択ボタンなし）にしてはならない。
- ルール:
  - 構成要素はファイル選択ボタン（必須）・ドロップ領域拡大チェックボックス（ドロップエリアがある時必須）・ドロップエリア・項目ラベル（必須）・要否ラベル・サポートテキスト・ファイル未選択メッセージ（必須）。
  - ドロップエリアはファイル選択ボタンの後ろに「または、このエリア内にドラッグ＆ドロップ」のテキストを伴う。
  - ファイル選択ボタンとドロップ領域拡大チェックボックスの間は少なくとも56 CSS px 空ける（ドロップエリアの幅は任意）。
  - ファイル選択時は選択ファイルサマリーと、解除ボタン・ファイル名・ファイルサイズ等メタ情報を持つ選択ファイル一覧（番号付きリスト）を表示する。
  - ファイル選択ボタンに関するエラー時はエラーテキストが必須で、ファイル単位のエラーはそのファイル名の下にエラーテキストを表示する。
  - ドラッグ＆ドロップの範囲をウィンドウ（ビューポート）全体に広げるかどうかはユーザーの判断に委ねる（拡大チェックボックス）。
  - 拡大時はファイルをドラッグしたカーソルがビューポートに重なるとビューポート全体がドロップエリアとなり、ドロップを促すメッセージを表示する。
  - カスタマイズする場合でも必ずファイル選択ボタンを配置し、ドラッグなしのシングルポインタで選択を完遂できるようにする（WCAG 2.5.7）。
- 文言: 「または、このエリア内にドラッグ＆ドロップ」「ドロップ領域を全画面に広げる」「このエリア内にファイルをドラッグ＆ドロップ」。
- 出典: `md/components/file-upload/index.md` — 「概要」ユースケース、「使い方」外観（コンポーネント要素：通常時／ファイル選択時、エラー）、ドラッグ＆ドロップの範囲の拡大、「アクセシビリティ」（必ずファイル選択ボタンを配置し、ドロップエリアのみで展開しない）

## スイッチ / Switch
- 用途: 切り替えたら即座に反映され、その場で目視で結果を把握できる設定項目（表示フィルターのオン・オフ、位置情報の利用許可、摂氏・華氏やリスト表示・カレンダー表示など2択の切り替え）。
- 使わない場面: 操作したその場で結果が分からないもの、保存・送信ボタンなどの確定操作を要するものはチェックボックスやラジオボタンを使う。
- ルール:
  - スイッチは切り替えた結果が即座に反映され、その場で確認できる設定にのみ使う。
  - 2つの選択肢の切り替えに使う場合は両方の選択肢にラベルを表示する。
  - 確定操作（保存・送信）を伴うフォームの項目にはスイッチを使わない。
- 文言: ラベル例「やさしい日本語に変換する」、2択例「リスト表示」「カレンダー表示」。
- 出典: `md/components/switch/index.md` — 「概要」ユースケース、注意が必要なケース、関連コンポーネント

## ボタン / Button
- 用途: 主にアクション実行またはページ遷移のトリガー。重要度に応じて塗り／アウトライン／テキストのスタイルを使い分ける。
- 使わない場面: 不要な無効化（`disabled`）は避ける。アクションボタンで「閉じる」を作らない（ノティフィケーションバナー側の規定）。
- ルール:
  - サイズは Large（最小幅136px・高さ56px）・Medium（96px・48px）・Small（80px・36px）・X-Small（72px・28px）で、最小幅と最小高さを保つ。
  - ボタン幅はラベルの左右 padding による可変長とし、ラベルが複数行になる場合は高さが増加する。
  - ターゲット領域は44 CSS px 以上を保ち、44px に満たない Small・X-Small は上下に余白を設けて確保する。
  - 塗りボタン（色付き背景＋White ラベル）＝プライマリー（重要度高）、アウトラインボタン＝セカンダリー（中）、テキストボタン（透明＋下線ラベル）＝ターシャリー（低）とするのが最も明確な階層である。
  - スタイルは重要度だけでなく、画面内・フロー全体での役割も加味して選ぶ（例: フローを進める遷移ボタンを、ヘッダーのログイン／ログアウト等の機能ボタンより優先）。
  - 同じスタイルで重要度が等しいボタンを並べる場合は配置で優先度を表し、サイト内で一貫した配置ルールを設計して適用する。
  - 塗りボタンが強すぎる場合はアウトラインボタンとテキストボタンで対応し、プライマリーとセカンダリーの区別はボーダーの太さや二重線で示す（色の違いのみにしない）。
  - プライマリーボタンは画面内で最も重要なアクションに使い、1画面につき原則1つまでとする。
  - セカンダリーボタンはプライマリー以外の選択肢に使い、同時に原則最大3つまでとする（4つ以上になる場合はフロー設計を見直す）。
  - 異なる文脈のセカンダリーは上記の数に含めず、文脈ごとに同時使用原則3つまでとする。
  - ターシャリーボタンはフローやアクションを中断・中止するキャンセル行為に使い、1画面につき原則1つまでとする。
  - プライマリーが複数ある設計は見直し、最も適切なアクション1つだけをプライマリーにする。
  - デスクトップでは「OK」「完了」「次へ」など進めるボタンを右寄せ、「キャンセル」「中止」「戻る」など進めないボタンを左寄せに配置する（LTR前提）。
  - 右寄せのボタン群では右ほど重要度が高く、プライマリーを右端に置く。
  - ボタンが1つ（プライマリーのみ）の場合、フローの最初の画面やノティフィケーションバナーでは右端、モーダルダイアログや緊急時バナーでは中央に配置する。
  - ボタンが1種類の場合は基本的に塗りボタンを使う（サイトの配置ルールによりアウトラインも可、モーダル右上の「×閉じる」は数に含めない）。
  - 2種類の場合はデスクトップ・モバイルともプライマリーを右端、セカンダリーを左端に置き、縦積みする場合は上にプライマリー、下にセカンダリーを置く。
  - 3種類の場合はデスクトップでプライマリーを右端、ターシャリーを左端、セカンダリーはプライマリーに対する選択肢なら右寄せ・ターシャリーに対するものなら左寄せにする。
  - モバイルではセカンダリー→プライマリーの順に縦積みし、ターシャリーのみ一番下に置く（セカンダリー2つは横並び可、サイト内で一貫させる）。
  - ボタンの無効化は避け、押下時に未完了の作業があればエラーメッセージで何をすべきかを案内する。
  - やむを得ず無効化する場合は、無効ボタンのすぐ近くになぜ無効か・どうすれば有効になるかを具体的に表示する。
  - `aria-disabled` を使う場合は押下できない実装と視覚的な無効表現が別途必要である（設計の再検討を優先）。
  - ラベルのテキストはボタン背景に対して4.5:1以上、ボタン自体（塗り・アウトライン）はページ背景に対して3:1以上のコントラスト比を確保する。
  - ボタンの重要度を色の違いのみで区別しない（塗り／アウトライン、太線・二重線など形状でも区別する）。
  - ページ遷移をもたらすボタンは hover 時に `cursor: pointer` にしてもよい（サイトの性質に応じて決定）。
  - ボタンにはテキストのラベルを持たせることを原則とし、アイコンだけのボタンには必ず代替テキスト（`alt` または `role="img"`＋`aria-label`）を指定する。
  - フォーカス順序はDOM順とし、視覚順との不一致はレスポンシブで許容される程度に留め、並べ替えはCSSで行う。
  - フォーカス順序の変更を目的に `tabindex` を使わない（使ってよい値は `-1` または `0`）。
  - ターゲットサイズは隣接要素と重複なく44×44 CSS px 以上を確保し、ボタン以外のリンク要素も最低24×24 CSS px 以上を確保する。
- 文言:
  - ラベル例: 「次へ」「完了」「確定」「キャンセル」「戻る」「前へ」「同意する」「利用規約に同意して新規登録する」。
  - 無効化時の補足例: 「名前と生年月日を入力すると送信ボタンを押せるようになります」。
- 出典: `md/components/button/index.md` — 「概要」、「使い方」仕様（サイズ／幅／ターゲット領域）、使い方（重要度に合わせたスタイルの使用／効果的な使用方法／ボタン配置の考え方／重要度に応じたボタンの並べ方／ボタンの配置と順序／異なる文脈としてのセカンダリーの配置／ボタンの無効化における注意点）、「アクセシビリティ」（コントラスト要件／色の違いのみで区別しない／無効ボタンはタブフォーカスでアクセスできない／aria-disabled の注意点／pointer／アイコンだけのボタンに代替テキスト／フォーカス順序と表示順序／ターゲットサイズの確保）

## ノティフィケーションバナー / Notification Banner
- 用途: サイト／サービス全体、またはページや要素単位の重要度の高い情報を、ユーザー操作に関わらずサービス側から提示する（メンテナンス通知、ユーザーの対応が必要な情報の通知とアクション誘導）。
- 使わない場面: ユーザーの生命・財産に関わる緊急告知は緊急時バナーを使う。複雑で付加的なリンクやアクションへの誘導には使わない。
- ルール:
  - タイプはサクセス（滞りない完了）・エラー（正しく完了しなかった）・警告（注意喚起・警戒情報）・情報提示1（プライマリーカラー）・情報提示2（ニュートラルの黒）で、各タイプのカラーはセマンティックカラーを使う。
  - デザインスタイルはスタンダード（角丸ボーダー）とカラーチップ（左辺だけ太線）から、サービスのトンマナに合わせて選ぶ。
  - バナーアイコンとバナータイトルは必須、バナーデスクリプションは任意、年月日・閉じるボタン・アクションボタンはオプションである。
  - 年月日は掲載日時に限らず掲載期間等にも使え、月日のみ・年月のみでもよい。
  - アクションボタンの個数に制限はないが、画角の狭いデバイスやラベル文字数を考慮した個数にとどめる。
  - アクションボタンで「閉じる」を作らず、非表示には「閉じる ×」パーツを使う。
  - 詳細ページなどへのリンクがある場合はプライマリーボタンを単一で追加し、ボタンを含むバナー全体をクリッカブルエリアにする（閉じる×の領域のみ非表示用）。
  - 選択的な行動を提供する場合はプライマリーボタンとセカンダリーボタンを使い、クリッカブルエリアはボタンのみとする。
  - リンクがない場合はクリッカブルエリアも Hover 状態も持たない。
  - 閉じるボタンを使う場合は閉じたことをサービスが記憶して非表示を持続させ、ユーザー自身の操作で再表示できる救済措置を用意する。
  - 通常はページ上部のファーストビューで必ず見える箇所に配置する。
  - 特定のコンテンツに関連する場合はそのコンテンツセクション内に配置してよい。
  - `position: fixed` / `sticky` でスクロール追従させる場合は必ず「× 閉じる」パーツを併用する。
  - 前景要素のコントラスト比は、テキストは4.5:1以上、非テキスト（外枠・アイコン）は3:1以上を確保する。
  - スタイルはサービス内で設定し一貫性を保ち、視認性が不十分な場合は背景色を使う。
  - モバイルではできる限り簡素化し、シンプルなインタラクション構成にする。
  - トップページの「重要なお知らせ」で使う場合は、過度な装飾を避け情報属性を持たないパターン（ニュートラルカラー）を選ぶ。
- 文言: タイトル例「登録手続きはすべて完了しました」（サクセス）、「操作を完了できませんでした」（エラー）、「偽SNSアカウントにご注意ください」（警告）、「登録期間が延長されました」（情報提示）、アクション例「了解しました」。
- 出典: `md/components/notification-banner/index.md` — 「概要」、「使い方」ノティフィケーションバナータイプ／デザインスタイル、仕様（パーツ／リンクやアクション／リンクがない場合／リンクがある場合）、使い方（配置場所／コントラスト比に配慮した作例／画面内に固定しスクロール追従するような表示／スタイルのバリエーション／重要なお知らせコンテンツで使用した作例）

## 注釈ブロック / Notice Block
- 用途: 強調された補足情報。手続きフォームの入力内容に対するヘルプ、入力時に必要な資料の例示、入力内容の具体例や選択肢の違いが分かる例など、極めて有用な情報を補足するとき。
- 使わない場面: 入力可能な文字種など入力・操作そのものの条件や制約はインプットテキストのサポートテキストを使う。本文の調子を変える装飾（コラム的な文脈切替や本文強調）として使ってはいけない。
- ルール:
  - 注釈ブロックのボーダーは補足情報であることを示すためのもので、本文の強調目的に使わない。
  - 読まなくても手続きを進められる補足情報を折りたたむ場合は、注釈ブロック内にディスクロージャーを入れてよい。
  - ディスクロージャーの内容が必ず展開しないといけない重要情報なら、ディスクロージャーは使えない。
  - バリエーションとして、本文のみ、タイトル＋本文、ディスクロージャー内包の形がある（図例）。
- 文言: 例「申し込みにあたっての注意事項」「有効期限が過ぎている書類は使用できません。」
- 出典: `md/components/notice-block/index.md` — 「概要」ユースケース、注意が必要なケース、関連コンポーネント

## 緊急時バナー / Emergency Banner
- 用途: ユーザーの生命や財産に影響をもたらす事象など、直ちに知らせなければならない緊急性の高い告知のため、サイト本来のコミュニケーションを中断してでもファーストビューを占有して注意を促すとき。
- 使わない場面: 長期間掲載する必要のあるメッセージ、緊急性の高くない通知（例: 「年末年始の営業時間について」）はノティフィケーションバナーを使う。
- ルール:
  - セマンティックカラーのエラー（Error）を使う。
  - ユーザーが非表示にすることはできない（閉じるボタンなし）。
  - サイトのトーン＆マナーとは少し異なる、違和感のある誘目性の高いスタイルを設定する。
  - バナータイトル（必須）は内容の重要性が分かる具体的なものとし、先頭に「【緊急】」を置く。
  - タイトルはモバイルでも2行に収まる全角30文字以内程度とする。
  - 年月日などには掲載日以外に更新日時も記載できる。
  - バナーデスクリプション（必須）は概ね全角100文字程度以内とし、それ以上は緊急情報ページを作成してリンクする（タイトルと合わせてSNSに全文配信できる程度が目安）。
  - アクションボタンはリンクがある場合必須で、最小幅は利用可能な表示幅の50%（モバイルは100%）とし、中央に配置する。
  - クリッカブルエリアはアクションボタン部分のみで、リンク先は1つまでとする。
  - ファーストビューで全ユーザーが最初に確実に認知できるページ上部に配置する（ヘッダーより上でもよい）。
  - ノティフィケーションバナー等ほかの通知が上部にある場合はそれらより上に置き、十分なスペースを取る。
  - 複数設置できるが緊急事態のみに限る。
  - タイトルは本文を読む前に一目で警告内容の概要が伝わるようにし、「緊急のお知らせ」のような抽象的な表現にしない。
  - 長期間にわたって掲示しない（アラート疲れを招くため）。
  - バナーデスクリプションは見出しや箇条書きで構造化し、端的に認知できる構成にする。
- 文言: タイトルは「【緊急】」から開始。良い例「○○地区に避難準備情報が発令されました」、悪い例「緊急のお知らせ」「年末年始の営業時間について」。アクション例「避難所の地図を確認」。
- 出典: `md/components/emergency-banner/index.md` — 「概要」、「使い方」仕様（パーツ／バナーのクリッカブルエリア）、使い方（配置／ページ上部への配置／タイトル／長期間に渡って掲示しない／緊急性の高い情報以外に使わない／長すぎるバナーデスクリプションを避ける／バナーデスクリプションの構成）

## ステップナビゲーション / Step Navigation

- 使わない場面: 一時的な処理の待機状態はプログレスインジケーター、順番に並んだページ・コンテンツの前後移動はページナビゲーションを使う。
- ルール:

  - 現在のステップ・完了・スキップ・エラーなどの状態を示す。
  - レイアウトは横並びと縦並びがある（図例）。
- 文言: ステップ名例「①基本情報入力」「②利用規約の確認」「③本人確認」「④顔写真の登録」「⑤申請情報の入力」。

## プログレスインジケーター / Progress Indicator
- 用途: ユーザーのアクションに対して処理進行中であることを通知する（データ取得リクエストの応答待ちなど）。
- 使わない場面: 複数ステップからなる手続き全体の進行状況はステップナビゲーションを使う。スケルトンUIは使わない（代わりにプログレスインジケーターを使う）。

  - ロード待ちの画面でスケルトンUIを使用せず、複数データを待つ画面でもプログレスインジケーターで処理中を示す。
- 文言: 「読み込み中」「生成中」。

## テーブル／データテーブル / Table, Data Table
- 用途: 構造化されたデータや情報を行と列で表示するとき、データを比較するとき、大量のデータを一覧表示し選択・編集・並び替え等を行うとき（データテーブル）。
- 使わない場面: 単なる名前–値のペアは説明リストを使う。レイアウト目的で使わない。
- ルール:
  - 構成要素はテーブルヘッダー・ヘッダーセル・データセル・フロントアイコン・ソートアイコン・エンドアイコン。
  - サイズは Default と Dense があり、情報を多く表示したい場合は Dense を選べるが、タッチ操作想定では狭くて操作しにくい点に留意する。
  - テーブルヘッダーとデータセルは黒いボーダーで明確に区切り、ヘッダーセルのテキストは太字にする。
  - セルの結合は最小限にし、データテーブルでは原則として結合しない。
  - テキストは縦方向を上寄せにし、横方向は通常左寄せ、数値や日付等は右寄せとすることがある。
  - 必要に応じて行／列のストライプ表示ができるが、縦方向の結合があると行ストライプ、横方向の結合があると列ストライプはできない。
  - ストライプ・ホバーハイライト・行選択がある場合、ボーダーと背景色のコントラスト比が3:1を下回らないようにする。
  - テーブル幅がコンテンツ幅を超える場合はテーブル領域内かページ全体の横スクロールかを選び、モバイルではテーブル領域内の横スクロールとしてスクロールを促すシャドーを表示する。
  - セル内の文字位置揃えや縦書き風表示のために空白文字・改行文字を使わない。
  - リンクはセル単位で、リンクが1つならセル全体をリンク領域にでき、2つ以上なら文字列ごとのリンクにする。
  - リンク表示はリンクテキストと同じ下線付き青テキストとし、大きさ等に応じて下線なし青または下線付き黒も可とする。
  - 行全体をリンクにすることはできない。
  - マウスが乗った行／列をホバーハイライトできる。
  - 行の選択は行頭のチェックボックスで行い、選択行はハイライト表示する。
  - テーブルヘッダー先頭に全行選択チェックボックスを置け、選択・未選択が混在する場合は `indeterminate` のマイナス表示にし、その状態で押すと全行を選択する。
  - ソート可能な列のヘッダーセルは下線付きテキストとソートアイコンで示し、昇順・降順・未ソートに応じたアイコンを表示し、テキストとアイコンをクリッカブルエリアにする。
  - 列への追加アクションはエンドアイコンの縦三点リーダーでメニューリストボックス等を展開し、操作は APG の Menu Button Pattern に準ずる。
  - できるだけシンプルな構造で作り、グループ見出し行の差し込みや入れ子・1レコード複数行の構造を避け、表の分割・別表化・セル内の構造化テキスト・1行1レコードで表現する。
- 文言: 特記なし（別表へのリンク例「別表：市民健康フェア参加料金」）。
- 出典: `md/components/table/index.md` — 「概要」ユースケース、注意が必要なケース、「使い方」コンポーネント要素、外観（サイズ／テーブルヘッダー、ヘッダーセル／セルの結合／テキストの配置／ストライプ表示／テーブルの幅がコンテンツ幅よりも大きい場合）、コンテンツ（テキスト／リンク）、ふるまい（ホバーハイライト／行の選択／すべての行を選択する／ソート／縦三点リーダーメニュー）、「アクセシビリティ」（シンプルな構造で作る）

## テーブルコントロール / Table Control
- 用途: 主にデータテーブルの周りに置き、キーワードで表示内容を絞り込む・1ページあたりの表示件数を変更する・行データへの操作やページ移動をまとめて提供するとき。
- 使わない場面: 行の選択や列の並び替えなどテーブル内で完結する操作はテーブル／データテーブルの機能を使う。複数条件を組み合わせた詳細検索は検索ボックスを使う。
- ルール:
  - テーブルコントロールの検索はキーワードによる絞り込みに限る。
  - コントロールはテーブルの上下に配置する（図例: 上に検索フィールド＋「検索」塗りボタン＋件数＋「リセット」リンク、右に「印刷」「CSVダウンロード」「新規追加」のアウトラインボタン、下にカウンター付きページナビゲーションと表示件数切り替え）。
  - 提供コントロールは精査のうえで追加・拡張予定である。
- 文言: 図例「検索」「25 件」「リセット」「印刷」「CSVダウンロード」「新規追加」「表示件数 10件 50件 100件」。
- 出典: `md/components/table-control/index.md` — 「概要」ユースケース、注意が必要なケース、関連コンポーネント

## ページナビゲーション / Page Navigation
- 用途: 複数に分割されたページやコンテンツを前後移動で表示する（一覧・テーブルの表示単位切り替え、連続する記事などの前後移動、カルーセル・イメージスライダーのスライド切り替え）。
- 使わない場面: 一連の手続きの現在位置と流れの提示はステップナビゲーションを使う。
- ルール:
  - 全体に対する現在位置を「1/24」「13ページ（全24ページ）」のように示すことができる。
  - 順番に並んだコンテンツの前後移動では、コンテンツ名をボタンラベルに含めてよい。
  - 前または次のページが存在しない場合、ボタンを無効化（disabled／非活性化）せず非表示にする。
  - パターンとして「前のページ／カウンター／次のページ」リンク、矢印のみの円形ボタン＋カウンター、「前の3件／次の3件」、コンテンツ名を持つアウトラインボタンがある（図例）。
- 文言: 「前のページ」「次のページ」「13 / 24」「前の3件」「次の3件」。
- 出典: `md/components/page-navigation/index.md` — 「概要」ユースケース、注意が必要なケース、関連コンポーネント

## アコーディオン / Accordion
- 用途: 同種のセクションが連続するとき、一覧として並べつつ各コンテンツを折りたたんで一覧性を高める（よくある質問、更新履歴、申請者属性ごとの個別説明など）。
- 使わない場面: 表示領域をコンパクトにするためだけには使わない。内容が重要なとき（折りたたみ側に重要情報がある）には使わない。独立した単一セクションのみには使わない。セクション内の一部を折りたたむ場合はディスクロージャーを使う。
- ルール:
  - ヘッダーで概要が示され、ボディが追加・補足情報になる合理的理由がある場合だけ使う。
  - 重要な情報は原則として最初から隠さずに表示する。
  - 単一セクションでの使用は避ける（運用途上で一時的に1セクションだけになるのは許容）。
  - 構成要素は開閉アイコン（必須、ヘッダーの左）・ヘッダー（必須）・ボディ（必須）・リターンリンク。
  - 開閉アイコンは L・M・S・XS の4サイズで、画面サイズやコンテンツの性質・ボリュームで使い分ける。
  - アコーディオン内にディスクロージャーは配置できる。
  - リスト内・テーブル内・アコーディオン内・ディスクロージャー内にアコーディオンを配置してはいけない。
  - ヘッダーにはコンテンツを要約した概要文を記載する。
  - ボディには見出し・段落・リスト・テーブルなど様々なコンポーネントを配置できる。
  - リターンリンクのラベルはヘッダーに「の先頭に戻る」を加えた形にし、リンク先はヘッダーへのページ内リンクとする。
  - ページ読み込み時に開いておくか閉じておくかを定める（先頭を開いておくと後続も折りたたまれていることを示唆できる）。
  - 実装には `<details>` 要素を使い、カスタム実装の場合はキーボードだけで開閉でき WAI-ARIA を付与する（APG Accordion Pattern 準拠）。
- 文言: ヘッダー例「会員登録の手順は？」「2025年11月5日 軽微な問題を修正しました」、リターンリンク例「『会員登録の手順は？』の先頭に戻る」。
- 出典: `md/components/accordion/index.md` — 「概要」ユースケース、注意が必要なケース、「使い方」コンポーネント要素（サイズバリエーション／リターンリンクの使い方）、配置（良い例／悪い例）、コンテンツ（ヘッダーは概要文にする／ボディ内にはさまざまなコンポーネントを配置できる／リターンリンクのラベルはヘッダーと揃える）、ふるまい、実装

## ディスクロージャー / Disclosure
- 用途: メイン情報に対する補足・注釈などの追加情報（特定条件のみの例外説明、グラフの元データ表、動画の文字起こし）や、メイン機能に対する詳細オプション（詳細設定、詳細検索）を折りたたんで提示するとき。
- 使わない場面: 表示領域をコンパクトにするためだけには使わない。展開が必須となる重要な内容には使わない。セクション全体を折りたたむ場合はアコーディオンを使う。
- ルール:
  - 展開しなくてもセクション内の地の文章・コンテンツだけで必要最低限の情報が伝わるようにする。
  - 構成要素は開閉アイコン（必須、タイトルの左）・タイトル（必須）・コンテンツ（必須）・リターンリンク（コンテンツ末尾）。
  - リターンリンクは、コンテンツ終端を明示する必要があるとき、コンテンツが長く文脈を見失う可能性があるとき、タイトルに戻って閉じる操作が必要なときに使える。
  - ディスクロージャーは入れ子にでき、アコーディオン内にも配置できる。
  - ディスクロージャー内にアコーディオンを配置してはいけない。
  - タイトルはコンテンツを要約した簡潔で説明的なラベルにする。
  - 「詳細を見る」「もっと見る」のように動作だけを示すタイトルは避ける。
  - 開閉状態でタイトルを変えず（「〜を開く／〜を閉じる」にしない）一定のラベルにする。
  - リターンリンクのラベルはタイトルに「の先頭に戻る」を加えた形とし、リンク先はタイトルへのページ内リンクとする。
  - 実装には `<details>` 要素を使い、カスタム実装の場合はキーボードで開閉でき WAI-ARIA を付与する（APG Disclosure Pattern 準拠）。
- 文言: 良い例「補足説明」「設定オプション」「ピックアップ一覧」、避ける例「詳細を見る」「もっと見る」「ピックアップを開く／閉じる」、リターンリンク例「『ピックアップ』の先頭に戻る」。
- 出典: `md/components/disclosure/index.md` — 「概要」ユースケース、注意が必要なケース、「使い方」コンポーネント要素（リターンリンクの使い方）、配置、コンテンツ（タイトルは簡潔で説明的にする／アクションを示唆することは避ける／開閉状態にかかわらず一定にする／リターンリンクのラベル）、ふるまい、実装

## 説明リスト / Description List
- 用途: 「説明したいこと」と「その説明文」のペアが複数連なるコンテンツ（用語集、FAQ、仕様書の項目名と内容、プロフィール情報、設定項目、申請内容の確認画面などの名前と値のペア）。
- 使わない場面: データの比較や行列構造が必要ならテーブル、セクションの主題を示すなら見出し、用語と説明のペアでない列挙・階層なら箇条書きリスト、複数の情報やリンク・選択操作を含む項目ならリソースリストを使う。
- ルール:
  - 名前と値（用語と説明）のペアを1項目として数え、それが繰り返される情報に使う。
  - 説明リストのタイトルで見出しを代用せず、見出しコンポーネントを使う。
  - マーカーなし／ビュレット付きのパターンがあり、項目名は太字で示す（図例）。
- 文言: 特記なし。
- 出典: `md/components/description-list/index.md` — 「概要」ユースケース、注意が必要なケース、関連コンポーネント

## 箇条書きリスト / List
- 用途: 1つ以上の項目を列挙するとき。順不同ならリストマークタイプ、法律の条文・利用規約・ガイドライン・手順など項番自体が情報として必要なら項番タイプ。
- 使わない場面: HTML の `<ol>` 要素や CSS カウンターによる項番は使わない。タイトル以外の情報やリンク・選択操作を含む項目はリソースリスト、名前と説明のペアは説明リストを使う。
- ルール:
  - すべて `<ul>`／`<li>` 要素で実装し、項番は `<li>` 内に地のテキストとして記載する。
  - `<ol>` 要素および CSS カウンターによる項番を使わない（コピー不可・項番の意図しない変化等のため）。
  - リストマークタイプは入れ子の深さに応じてインデント（マーカー1: 0、マーカー2: 16/24/32、マーカー3: 48/56）を設け、3種類のマーカーを使い分ける。
  - 項番タイプも入れ子の深さに応じてインデント（0/24/32/48/72）を設ける。
  - 項番マーカーの幅はデフォルトで全角2文字分とし、3桁以上になり得る場合は必要に応じて広げる。
  - 項番は数字・丸付き数字・ローマ数字・アルファベット・ひらがな・カタカナや各種括弧・ピリオド・ハイフン・コロンなど任意のフォーマットで記述できる。
  - 項番自体をリンクにしてもよい。
  - 各項目の上下間隔は3段階（12・8・4）から設定できる。
  - 中黒（・）やテキストの項番＋改行、スペースでのインデントで箇条書きを再現せず、箇条書きリストを使う。
  - 入れ子は親の `<li>` 内に子の `<ul>` を置く正しいマークアップにする。
- 文言: 項番例「1章 はじめに」「01 本書の構成と使い方」。
- 出典: `md/components/list/index.md` — 「概要」ユースケース、注意が必要なケース、「使い方」リストマークタイプ／項番タイプ（階層と表示／項番の記載）、リストアイテム間の間隔、実装、「アクセシビリティ」（箇条書きをテキストで表現せず／ol要素は使わず／適切な入れ子）

## モーダルダイアログ / Modal Dialog
- 用途: 削除などの破壊的な操作の押し間違い防止、モーダルダイアログ内で完結する短いメッセージの表示。表示中はダイアログ内しか操作できない。
- 使わない場面: 補足情報の提示（先にサポートテキスト・注釈ブロック・ディスクロージャーを検討）、処理の完了やステータス変化の通知、告知情報（緊急時バナー／ノティフィケーションバナーを使う）、ダイアログ外の情報を読まないと判断できない場合、フォームを入れる場合、ナビゲーションメニューの表示（ドロワーやハンバーガーメニューボタンを使う）。
- ルール:
  - ユーザーのボタン押下なしにモーダルダイアログを表示しない。
  - 処理の完了やステータスの変化などユーザーの判断を必要としない内容をモーダルダイアログで表示しない。
  - 告知情報は一時表示せずページ内で常に伝える。
  - 「OK」「はい」「いいえ」「キャンセル」などのアクションボタンがある場合は閉じるボタンを使わず、閉じるボタンはアクションボタンがないときだけ使う。
  - 確認ダイアログだけを安全対策にせず、誤削除しない設計や取り消し・復元ができる設計を検討する。
  - ダイアログ外の情報を読みながら判断する必要がある場合は、判断材料と操作を同じ画面に表示する。
  - モーダルダイアログにフォームを入れず、フォームはページ上に直接表示する。
  - ボタンが1つだけの場合はプライマリーボタンを中央に配置する（ボタンの規定）。
- 文言: 例 タイトル「対応が必要なお手続きがあります」、本文「マイページよりお知らせの内容を確認し、期限までにご対応をお願いいたします。」、ボタン「OK」。
- 出典: `md/components/modal-dialog/index.md` — 「概要」ユースケース、注意が必要なケース、関連コンポーネント; `md/components/button/index.md` — 1種類のボタンだけを使用する場合

## 見出し / Heading
- 用途: ページ全体の主題（レベル1）やセクションの主題（レベル2〜6）を示し、ページのコンテンツ構造を示すとき。
- 使わない場面: 項目の列挙・階層は箇条書きリスト、用語と説明の繰り返しは説明リストを使う。物語や発話録など原文に見出しがない文書には無理に挿入しない。
- ルール:
  - 構成要素はショルダー・見出しテキスト（必須）・サブタイトル・リードアイコン・チップ・飾り罫。
  - 見出しは `<h1>`〜`<h6>` に対応し、階層が深くなるごとにレベルが増え、6階層まで形成できる。
  - あるレベルの見出しから、次に同じまたは上位レベルの見出しが出るまでを1セクションとする。
  - `<title>` 要素に相当するページの主題をレベル1見出しにする（例: `<title>ページの主題｜サイト名</title>` → `<h1>ページの主題</h1>`）。
  - レベル2以降はセクションの主題を記述し、セクションごとに見出しを置く（原文に見出しがない場合を除く）。
  - 見出しレベルとフォントサイズは別々に定義し、対応関係はスタイルガイドで定義する。
  - リードアイコン・チップは見出しの左、飾り罫は見出しの下に表示できる。
  - ショルダーとサブタイトルは `<p>` 要素で記述し `<hgroup>` で見出しとグループ化し、`<h1>`〜`<h6>` にしない。
  - 見出しレベルを飛ばさず、直下には1段階下のレベルだけを置く。
  - セクションの主題は箇条書きリストのインデントや説明リストのタイトルで代用せず、見出し要素を使う。
  - 見出しを伴うコンポーネントを動的に挿入する場合は、ページのセクション構造に合わせて見出しレベルを調整する。
- 文言: 特記なし。
- 出典: `md/components/heading/index.md` — 「概要」ユースケース、注意が必要なケース、「使い方」コンポーネント要素、仕様、見出しによる構造化、文字サイズとスタイル、ショルダーとサブタイトル、「アクセシビリティ」（見出しレベルを飛ばさない／箇条書きリストと使い分ける／説明リストと使い分ける／動的に挿入する場合／無理に見出しを挿入しない）

## パンくずナビゲーション / Breadcrumb
- 用途: ウェブサイトの階層内でユーザーの現在の位置を表示する。
- 使わない場面: 記載なし。
- ルール:
  - ヘッダーとページ見出しの間に配置する。
  - 長さは階層の深さやページ見出しの文字長に依存するため、コンテンツエリア幅を超える場合に改行する仕様を前提とする（デスクトップは改行）。
  - モバイルではデスクトップと同様の改行仕様、または改行なしの横スクロール仕様の併用のどちらかで実装する。
  - 改行仕様の場合はページ上部またはページ下部に配置する。
  - 多くのページで長いパンくずが想定される場合は、コンテンツが押し下げられないよう改行なしの横スクロール仕様にする。
  - 横スクロール仕様で実装した場合は、ページ下部（フッターエリアの上部）に改行仕様のパンくずナビゲーションも配置する。
- 文言: 特記なし。
- 出典: `md/components/breadcrumb/index.md` — 「概要」、「使い方」配置と仕様（デスクトップ／モバイル：改行での仕様／横スクロールでの仕様）

## チップラベル / Chip Label
- 用途: 状態や状況を示すキーワードを表示し情報の分類・整理を効率化する（申請一覧の状態「受付中・審査中・完了」、テーブル行の分類「新着・更新・終了」、お知らせ種別・注釈種別・記事タグなどのカテゴリ表示）。
- 使わない場面: ユーザーが選択または入力した値をアイテム化して並べる場合はチップタグを使う。
- ルール:
  - 色だけで意味を伝えず、必ずテキストで状態や分類を明示する。
  - 多くの色を使いすぎず、必要な場合にのみ色を使う。
  - アクセントカラーを使う場合は文字や輪郭と背景色のコントラストを確保する。
  - スタイルは白地＋色付きボーダーのカプセル型、淡色背景＋色ボーダーの角丸、濃色塗り＋白文字の直角などがある（図例）。
- 文言: 例「受付中」「審査中」「完了」「新着」「更新」「終了」「開始前」「作業中」「保留中」「中止」「提出済」「承認済」「却下」。
- 出典: `md/components/chip-label/index.md` — 「概要」ユースケース、注意が必要なケース、関連コンポーネント

## チップタグ / Chip Tag
- 用途: ユーザーが選択した項目（例: サイト内検索の絞り込み条件）や入力した値（例: メールの宛先）をアイテム化して並べ、個別に表示・削除しやすくするとき。
- 使わない場面: コンテンツの状態や分類を示す場合はチップラベルを使う。削除操作が不可逆な（元に戻す方法がない）場合は使わず、チェックボックスを検討する。
- ルール:
  - 選択内容を確認しながら不要なものだけを削除できるようにする（ラベルの後ろにバツマーク・図例）。
  - 人物を示す場合は先頭にアイコンを添えてよい。
  - 削除が不可逆な場合はチップタグを使わない。
- 文言: 例「検索条件：」の後に「現行法令」「法令」「勅令」「関連度順」「10件」。
- 出典: `md/components/chip-tag/index.md` — 「概要」ユースケース、注意が必要なケース、関連コンポーネント

## カード / Card
- 用途: 単一の主題に関するコンテンツをまとめるコンテナ。画像等メディアとテキストをグループ化したいとき、記事・商品・画像ギャラリーなど類似アイテムを一覧・グリッドで提示するとき。
- 使わない場面: データの詳細な比較・分析はテーブルを使う。
- ルール:
  - 構成は最大4パーツ: コンテナ（必須）・イメージエリア・メインエリア（必須）・サブエリア。
  - イメージエリアとサブエリアを隣接させてはならない。
  - コンテナは必ず背景色と視覚的な外周をもつ（ドロップシャドウのみで境界を表現しない）。
  - コンテナの外周色は外側の背景色に対して3:1以上のコントラスト比を確保する（例: White 上の Gray-300 は2.1:1で不可）。

## 横断的に繰り返される原則

1. **プレースホルダーを使わず、入力条件・例はサポートテキストに書く** — インプットテキスト、日付ピッカー（注釈ブロックも「入力条件はサポートテキストへ」と規定）。
2. **要否ラベルは「※必須」「※任意」（全角米印始まり）で項目ラベルの隣に置く** — インプットテキスト、日付ピッカー、テキストエリア・セレクトボックス・ファイルアップロード（要否ラベルを構成要素に持つ）、チェックボックス／ラジオ（図例）。
3. **エラーテキストは項目の下に置き、「＊」から始め、具体的な内容と直し方を書く** — インプットテキスト、テキストエリア（超過文字数を表示）、日付ピッカー、セレクトボックス、ファイルアップロード（ファイルごとのエラー）。
4. **ラベルは端的に、必須の構成要素として表示する（単一項目で画面タイトルが説明している場合のみ省略可）** — テキストエリア、セレクトボックス、チェックボックス、インプットテキスト（項目ラベル必須）、日付ピッカー、ファイルアップロード。
5. **`disabled`（無効化）を使わない。どうしても使うなら近くに理由と有効化条件をテキストで示す** — ボタン、インプットテキスト（readonly も原則不可）、日付ピッカー、ページナビゲーション（無効化せず非表示）。
6. **選択系コンポーネントの使い分け** — 1つだけ選ぶ＝ラジオ（5個以下）、6個以上＝セレクトボックス、多数で絞り込み要＝コンボボックス、複数選択＝チェックボックス、即時反映＝スイッチ、確定操作あり＝チェックボックス／ラジオ（セレクトボックス、ラジオボタン、チェックボックス、スイッチ、コンボボックス）。
7. **色だけで意味や重要度を伝えない（形状・テキストを併用）** — ボタン（重要度）、チップラベル（必ずテキスト）、ノティフィケーションバナー（アイコン＋タイトル）、メニューリスト／モバイルメニュー（異なるアイコン形状）。
8. **コントラスト比: テキスト4.5:1以上、非テキスト（枠線・アイコン・ボタン形状）3:1以上** — ボタン、ノティフィケーションバナー、カード（外周3:1）、テーブル（ストライプ／ハイライトのボーダー3:1）、チップラベル。
9. **ターゲットサイズ44×44 CSS px 以上（リンクは最低24×24）** — ボタン（Small／X-Small も余白で確保）、リンク要素全般、テーブル（Dense はタッチ操作に注意）。
10. **重要な情報は隠さない。折りたたみはコンパクト化目的では使わない** — アコーディオン、ディスクロージャー、注釈ブロック（展開必須の内容にはディスクロージャーを使わない）。
11. **折りたたみの役割分担と入れ子制限** — セクション全体＝アコーディオン、セクションの一部＝ディスクロージャー。アコーディオンはリスト／テーブル／アコーディオン／ディスクロージャー内に置かない（アコーディオン、ディスクロージャー、注釈ブロック）。
12. **ユーザーの明示的な操作（クリック・ボタン押下）でのみ開く／変化させる。ホバー・フォーカス・値の変更で予期しない変化を起こさない** — モーダルダイアログ（ボタン押下なしに表示しない）、日付ピッカー（カレンダーはボタン押下のみ）、メニューリストボックス（クリックで展開）、インプットテキスト（値の変更で遷移・ダイアログを起こさない）、日付ピッカー（フォーカス自動移動・IME制御をしない）。
13. **ラベル・タイトルは中身を具体的に表す文言にし、抽象語や動作だけの表現を避ける** — 水平メニュー（「詳細」「その他」を避ける）、ディスクロージャー（「詳細を見る」「もっと見る」を避け、開閉で文言を変えない）、緊急時バナー（「緊急のお知らせ」は不可）、アコーディオン（ヘッダーは概要文）、目次（見出し文言をそのまま使う）、エラーテキスト（「入力に誤りがあります」は不可）。
14. **リターンリンクは「『〜』の先頭に戻る」でヘッダー／タイトルへのページ内リンク** — アコーディオン、ディスクロージャー。
15. **ボタンの重要度と配置: プライマリーは1画面1つ、進む操作は右・戻る／キャンセルは左、単独ボタンはダイアログ・緊急時バナーで中央** — ボタン、モーダルダイアログ、緊急時バナー、ノティフィケーションバナー（リンク時はプライマリー単一）。
16. **閉じる操作の扱い** — 「閉じる」はアクションボタンで作らず専用の閉じる×パーツ（ノティフィケーションバナー）、アクションボタンがあるモーダルには閉じるボタンを置かない（モーダルダイアログ）、緊急時バナーは閉じられない、ドロワーは「閉じる」ボタンで閉じる、ハンバーガーメニューは開くと「閉じる」表示。
17. **通知手段の使い分け** — 緊急かつ生命・財産に関わる＝緊急時バナー、常設・長期の重要情報＝ノティフィケーションバナー、補足＝注釈ブロック／サポートテキスト／ディスクロージャー、処理完了やステータス変化はモーダルで知らせない（緊急時バナー、ノティフィケーションバナー、モーダルダイアログ、注釈ブロック）。
18. **進行状況の表現の使い分け** — 手続き全体＝ステップナビゲーション、一時的な待機＝プログレスインジケーター（スケルトンUIは使わない）、ページ・コンテンツの前後移動＝ページナビゲーション、同一主題の観点切替＝タブ、サイト内移動＝水平メニュー（ステップナビゲーション、プログレスインジケーター、ページナビゲーション、タブ、水平メニュー）。
19. **構造化はネイティブなセマンティクスで行う** — `<details>` でアコーディオン／ディスクロージャー、`<h1>`〜`<h6>` をレベルを飛ばさず使う（見出し）、`<ul>` で箇条書き（`<ol>`・CSSカウンター・中黒テキスト不可）、テーブルはレイアウトに使わずシンプルな構造に、空白・改行で見た目を整えない（アコーディオン、ディスクロージャー、見出し、箇条書きリスト、テーブル、説明リスト）。
20. **情報の型に応じたコンポーネント選択（テーブル／説明リスト／箇条書き／見出し／カード／リソースリスト）** — 比較・行列＝テーブル、名前–値ペア＝説明リスト、単純列挙＝箇条書きリスト、主題＝見出し、メディア＋テキストの並列＝カード、複数情報・操作を含む項目＝リソースリスト（テーブル、説明リスト、箇条書きリスト、見出し、カード）。
21. **フォーカス順序は DOM 順。`tabindex` で並べ替えない、視覚順の変更は CSS で** — ボタン（`tabindex` は -1/0 のみ）、ファイルアップロード（ドラッグなしの単一ポインタ操作を保証）、日付ピッカー（APG 準拠のキーボード操作）、アコーディオン／ディスクロージャー（カスタム実装時はキーボード開閉と WAI-ARIA）、テーブル（Menu Button Pattern）。
22. **入力値は可能な限りエラーにせず正規化・受け入れる** — インプットテキスト（文字種を限定しない、自動変換は送信時、maxlength 不使用、コピペ禁止しない、メールアドレス分割しない）、日付ピッカー（全角→半角、ゼロ埋めの自動補正）、テキストエリア（上限はラベルで事前提示）。
23. **モバイルでは簡素化し、ハンバーガーメニューボタン＋ドロワー＋モバイルメニューで階層は浅く** — 水平メニュー、ヘッダーコンテナ、ハンバーガーメニューボタン、ドロワー、モバイルメニュー（2段階以上の階層を作らない）、ノティフィケーションバナー（モバイルは簡素に）、パンくず（横スクロール／改行）、テーブル（領域内横スクロール＋シャドー）。
24. **挙動の違う要素は見た目（アイコン）を明確に変え、サイト内で一貫させる** — メニューリスト、モバイルメニュー、ボタン（サイト内一貫の配置ルール）、ノティフィケーションバナー（サービス内でスタイル一貫）。
