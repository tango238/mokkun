# シナリオA（保育所入所申込）決定ログ

## ルールが沈黙していた点

1. **item の命名規則**: camelCase の英語名詞（applicantName, nursery1）にした。ローマ字・英語・日本語のどれか、複数の対象（保護者/児童）の接頭辞を付けるかは未規定。欲しいルール「item は英語 camelCase。主体が複数あるときは主体を接頭辞にする」。
2. **view / section / action の id 命名**: snake_case（application_form, to_confirm）にした。view 名の語彙（list/form/confirm/done/detail）や action id の付け方は未規定。
3. **氏名・フリガナの分割**: R-I10 はメール・電話・郵便番号のみ言及。氏名は「氏名」「フリガナ」各1項目にし、姓名分割はしなかった。ラベルは「保護者の氏名」と主体付きにした。分割基準が欲しい。
4. **メール確認欄（再入力）を置くか**: 置かなかった（R-I10 は分割禁止のみで、確認欄の是非は不明）。
5. **住所の粒度**: 都道府県・市区町村・番地を分けず1項目（width: full）。郵便番号からの自動補完は help に書いたのみ。住所を分けるか否かの規定がない。
6. **住所を「郵便番号→住所」の順に並べる/columns: 2 を使うか**: R-S13 は2列を許すが、他項目との整合を優先して全セクション columns: 1 にした。columns が現状未対応（レンダラー無視）なので判断材料も無い。
7. **width の割当**: 郵便番号 sm、電話 md、氏名 md、メール lg、住所 full、保育所 lg、就労時間 xs、勤務先 lg とした。R-I15 は「内容に見合わせる」のみで項目種別ごとの対応表がない。日付・ラジオ・チェックボックスに width を付けるか不明（付けなかった）。
8. **View あたりの Section 数と分割粒度**: 新規申込は7 Section（申込者・児童・保育所・理由・勤務先・添付・同意）。R-S02 は「1 Section 7項目以内」のみで、Section 数の上限・同意のように1項目だけの Section を許すかは未規定。
9. **複数ステップか1画面か**: 「ルールに従って決める」とあったが、入力画面を何ステップに分けるかの基準が無い（R-F01 は入力→確認→完了のみ）。1入力画面＋layout: sectioned にした。分割の判断基準（項目数、所要時間）が欲しい。
10. **layout: sectioned を使うか**: R-V12 は「多く長い画面」とだけあり、Section 数の閾値が無い。7 Section なので使った。
11. **確認画面は入力セクションをミラーするか**: R-F03 は「kind: readonly で作る」まで。入力の7 Section をどうまとめるか不明で、4 Section に再編した（申込者/児童/保育所/理由+勤務先+添付）。同意の確認項目は載せなかった。ミラー規則（同じ分け方か、まとめてよいか）が欲しい。
12. **確認画面の条件分岐項目**: 就労でない場合は勤務先を出さない、が確認画面では静的な値でしか書けない。確認画面の readonly で visibleWhen を使うか、モック値としてどのケースを見せるかが未規定。就労ケースを例示した。
13. **確認画面のモック値の作り方**: 実在しない氏名・住所・電話をどこまで具体的に書くか未規定。ダミーの仮名・example.jp を使った。
14. **確認画面で component に何を使うか**: value 表示用に text/date/status のどれを使うかの規定が無い。性別・理由など選択肢項目も text で表示ラベルを直書きした。
15. **完了画面の中身**: R-F04/R-V10 は成功メッセージまで。受付番号・状態・申込日を readonly の Section に置いたが、「次に何が起こるか（審査結果の通知時期）」を置く場所（note か description か）は未規定。
16. **受付番号の見せ方**: success メッセージと readonly の両方に載せた（重複）。どちらかに限るべきか不明。
17. **完了画面の導線**: primary を「申込一覧へ」1つ。「続けて申込む」を置くか（きょうだい申込など）は未規定。
18. **取り下げの置き場所と形**: 詳細画面の secondaryActions に danger＋confirm で置いた。R-F05 は取消操作に confirm を許すので適合と判断したが、「取り下げ」が primary になるべきか、一覧の rowAction に置くかは未規定。
19. **詳細画面に primaryAction が無くてよいか**: R-V01 は「1画面に1つ」と読めば必須に見える。主操作が破壊的操作（取り下げ）のとき primary を空にする、danger を primary にする、のどちらが正か規定が無い。primary なしにして、戻るを tertiary にした。
20. **詳細画面と一覧の関係**: detail を flow に含めず、list の rowActions から navigate するだけとした。nav は application_list にして「現在地」を一覧とした。詳細・参照系の View の位置づけ（nav をどれにするか、別 flow にするか）が未規定。
21. **詳細画面が参照する申込の特定**: どの申込を表示しているかをスキーマで渡す方法が無い。ダミー値固定。
22. **詳細で状態に応じて取り下げを出し分ける**: 「内定」「不承諾」では取り下げ不可にすべきだが、ボタンの出し分けルールが無い（R-V05 は無効化禁止だけ）。
23. **一覧の状態列の表現**: 一覧は kind: list のため status component が使えず文字列列にした（R-I12 は色に頼らず value に状態名を入れる、だが list では適用範囲不明）。
24. **一覧のフィルタ Section を置くか**: R-V13 は「基本形」。件数は少ない想定だが踏襲し、状態の segmented select だけを置いた。少件数のとき省略してよいか不明。
25. **一覧の primaryAction の placement**: sample に倣い header とした。使い分け（header/footer/sticky）の規定が無い。
26. **入力画面の placement: sticky**: sample に倣った。基準が無い。
27. **「申込をやめる」の confirm**: R-F05 は取り消せない操作限定。入力破棄はこれに当たるとして sample に倣い付けたが、下書き保存が無い場合の入力破棄を取り消せない操作と見なすかは判断。
28. **下書き保存 / resumable**: R-F07 は「長い手続き」。項目数約25で長いが、シナリオに記載が無いので resumable を付けなかった。「長い」の基準が無い。
29. **通知の日付**: 「〇月〇日」を具体日（11月20日）にしたが、実在日付を入れるか、固定日付を書いてよいか（古くなる）の規定が無い。variant は info にした（warning との使い分け規定なし）。通知に dismissible を付けない判断は R-A06 から導けた。
30. **app.header の userName**: ログイン済み保護者の氏名を入れた。ダミー個人名の可否・tenantName（自治体名）を入れるかが不明（入れなかった）。
31. **navigation の構成**: 「申込一覧」「新規申込」の2項目を1 group にした。完了/確認/詳細は含めない根拠が無い（暗黙に sample を踏襲）。group 名の付け方も未規定。ログアウト/ヘルプの置き場も不明。
32. **ナビラベルと title の一致（R-A01）**: ナビは view の title を使うので「保育所入所申込の一覧」「保育所入所の申込」と長くなった。title を短くするかナビ用 label を書くか、の優先が不明。
33. **flow の step label**: R-F02 に合わせ「申込内容の入力/確認/申込の完了」とした。view の title と step label を揃えるか（R-W07 は見出しとナビ）は不明。
34. **role の使い方**: roles に「保護者」を置き、flow と各 view に role を付けた。全 view に付けるか、1つのときは省くかが未規定。
35. **ログイン済みの扱い**: 本人情報（氏名・住所）を初期値で入れるか（default）、readonly で見せるか。シナリオに無く入力させた。ログイン情報の再利用ルールが無い。
36. **性別の選択肢**: 男/女/回答しない。R-I07 は任意ラジオの「あてはまるものはない」のみ。必須ラジオで「回答しない」を許すか、そもそも性別を聞くべきかの指針が無い。
37. **希望保育所 25 件の component**: 選択肢が「多く文字で絞り込みたい」のとき combobox（§5.1）だが、25 件で絞り込み要否は判断。select にした（6件以上→select）。閾値が無い。
38. **第2・第3希望を任意とした根拠**: シナリオは「第1〜第3希望」。第1のみ必須とし、同一保育所の重複禁止は help に書いた（バリデーションで表現できない）。
39. **希望入所日の component**: R-§5.1 の「近い期間から選ぶ」に当たり date＋calendar:true にした。「通知の締切と入所日の整合」は表現不可。
40. **生年月日の help**: 保護者と児童で例示年を変えた。同じ入力例を使うか不明。
41. **「その他」の自由記述の文字数**: R-I06 に従い 200 文字以内と help に書いたが、実際の制限値はシナリオに無いので仮置き。textarea の「質問を分割できないか」検討は適用外と判断。
42. **条件表示の置き場**: 「その他」は項目の visibleWhen、「就労」は Section の visibleWhen にした。項目単位かセクション単位かの使い分けが未規定。
43. **分岐の予告**: R-I13 に従い needReason の help に「就労を選ぶと勤務先の入力欄が表示されます」と書いた。「その他」の分も同じ help に混ぜるべきか不明。
44. **条件付き必須**: 「その他の理由」「勤務先名」は表示されたときだけ必須。required: true を付けたが、非表示時の必須扱いは仕様に書かれていない。
45. **添付書類の複数可**: file に multiple の正規キーが無く props: { multiple: true } にした。必須か任意か（就労のとき必須）も条件付き必須が表現できず任意（required なし）にした。
46. **同意項目**: 規約は checkbox required にした。規約本文へのリンクの置き場が無い（help に文言のみ）。同意を独立 Section にするか、送信直前の確認画面に置くかの規定が無い。
47. **同意を入力画面に置くか確認画面に置くか**: 確認画面に置く案もあったが、入力画面にした。
48. **エラー文（props.error）**: R-I14 は推奨だが、全項目に書くか代表だけかは不明。多すぎるため省略し、View の states.error だけ書いた。
49. **R-V09 のエラー文**: 「どこを見ればよいか」を「赤字の項目」と書いたが、赤字を前提にしてよいか不明（色だけに頼らない原則と衝突しうる）。
50. **states.empty と list.empty の重複**: 両方に同じ文言を書いた。どちらかで良いのか。
51. **ページサイズ**: pageSize 10。基準無し。
52. **一覧の列構成**: 受付番号・児童名・申込日・希望入所日・状態。sortable をどれに付けるかは R-S08 のみ（「並び替えできる列だけ」）。
53. **ボタン文言**: 「申し込む」（確定）、「新規に申し込む」、「申込をやめる」「入力に戻る」「申込一覧に戻る」。R-W02 の「戻る」の統一は一覧に戻る/入力に戻るの2種で揺れ得る。R-W01 の「動詞で終える」と「申し込む」が確定の意味を十分示すかも不明。
54. **見出し（title）の文体**: R-S 見出しは「動詞＋名詞」（schema-v2.md）。確認画面の見出しは「〜を確認する」にしたが、readonly Section の見出しが動詞で良いか不明（sample は「注文内容を確認する」と同様）。
55. **完了画面のタイトル**: sample に倣い完了文にした。
56. **状態 variant**: status の variant に primary を使ったが、受付済/審査中/内定/不承諾の色の割当ルールが無い（R-I12 は value 必須のみ）。
57. **日付の value の書式**: readonly の date は ISO（2026-11-07）で書いた。表示は和暦/西暦、書式が未規定。
58. **電話番号の value**: ハイフンなしで表示。表示時の整形ルールが無い。
59. **単位の置き方**: 「週の就労時間」の単位（時間）をラベル・format のどちらに入れるか。format に書いた。
60. **a11y / 多言語 / 外国語対応**: 公共サービスで必要になり得るがルールに無い（注: 範囲外かもしれない）。

## ルールが曖昧または矛盾していた点

1. **R-V01 と R-V03 と詳細画面**: primary は「1画面に1つ」、戻るは tertiary。詳細画面で primary を置くべき行動が無いとき、primary 無しが許されるのか（チェックリストは「primaryAction が1つ」と読める）。
2. **R-I04 と schema 説明**: R-I04 は「placeholder は使わない」とし example はサポートテキストに描画される、とあるが、02-schema-v2.md は example を「placeholder として使う」、コンパイル規則も placeholder 扱い。実際にどう描画されるか文書間で食い違う。
3. **R-S03（折りたたまない）と section.visibleWhen**: セクション visibleWhen が v2 では全体、旧フォーマットではフィールド単位、と2通りの意味が書かれている。「勤務先を入力する」の見出しも条件で隠れるのかが読み手により異なる（02 の表と schema-v2.json の description も不一致: JSON は「セクション単位の表示制御ではない」）。
4. **R-S06 と確認画面の値の型**: readonly の value に date を使うか text を使うかで表示が変わり得る。R-I08 は「表示系 component」と言うが、text で良いのか。
5. **R-S13（columns は1が基本）と sample（columns 2/3 多用）**: sample が基本形に反して見える。
6. **R-F05 と R-F06**: 取り消せない操作に限って confirm とある一方、取り消し・復元できる設計を先に検討とある。取り下げは「取り消せない」か（再申込可能かもしれない）の判断が業務依存。
7. **§5.1 のラジオ（5個以下）と「その他」の選択肢**: 理由5件はちょうど5で radio。5 を含むのは明確だが、「選択肢が多い/少ない」の線引きと combobox の条件が曖昧（25 件が select か combobox か）。
8. **R-I10 の「原則1つ」と R-I11 の「年月日は3分割で描画」**: 生年月日も分割されるが、分割描画と R-I10 の趣旨（分けない）の関係が不明。
9. **R-S02 の7個以内と申込者 Section**: 申込者は7項目ちょうど。目安なので許容と読んだ。
10. **R-V02（副アクション3つ以内）と tertiary**: tertiary は副アクションに数えるか。数えるなら詳細画面は2。数えない場合の上限が不明。
11. **R-I02（required を正しく付ける）と条件付き必須**: 表示されたときだけ必須の項目に required: true を付けてよいか、付けると非表示時にも必須と解釈される恐れ。
12. **R-A04（処理結果は通知に使わない）と締切告知**: 締切のお知らせは「常設・長期の重要情報」に当たる、と読んだ。日付が過ぎると失効する情報を常設とみなしてよいか。
13. **action.confirm の danger（02）と style: danger**: confirm.danger が true だと action style が danger に変換される、と02にあるが、R-F05 は `danger: true` を勧め、Action.style: danger も別にある。両方書くべきか。両方書いた（冗長の可能性）。
14. **R-F03「正規化した入力値は確認画面で見せる」**: 郵便番号から補完した住所は正規化に当たり確認画面に見せたが、補完を入力画面側でどう見せるか（readonly にするか）は R-I09 と競合しうる。

## スキーマで表現できなかった点

1. **郵便番号からの住所自動補完**: 挙動として書けない。help の文言のみ。
2. **相関バリデーション**: 第1〜第3希望の重複禁止、児童の生年月日と入所日の整合、締切日以降の申込制御。rules は個別項目の既存属性のみ。
3. **条件付き必須**: 「就労のとき添付書類が必須」を書けない。
4. **visibleWhen の複合条件**: equals 1つだけ。「就労または求職」のような OR や AND が書けない。
5. **file の複数指定の正規キー**: multiple は select/checkbox 用で、file は props 頼み。ファイル種別（PDF+画像）・容量上限も accept が `image` しか定義されない。
6. **一覧の状態列のバッジ表示**: kind: list の列に status/badge を使えない（文字列のみ）。
7. **一覧の rowActions の遷移先**: `to` が旧レンダラーで未対応（コンパイル規則）。どの申込の詳細を開くかの文脈（ID）も渡せない。
8. **詳細画面が対象申込に紐づくこと**: view にパラメータが無い。
9. **状態に応じたボタン出し分け**: 内定/不承諾では取り下げ不可、のような表示制御。
10. **取り下げ後の状態遷移**: action に実行結果（一覧の状態更新、完了メッセージ）を指定できない。kind: custom の挙動も記述不可。
11. **確認画面の入力値連動**: 入力した値の反映（確認が入力と同じ値になる）が書けず、ダミー値の直書きになる。条件分岐でも確認項目を切り替えられない。
12. **完了画面の受付番号の動的埋め込み**: 発行された番号の差し込み機構が無く固定文字列。
13. **ログイン済み利用者情報の初期値**: userName 等を項目の default に引用できない。
14. **規約の本文/リンク**: 同意項目に規約本文やリンクを付けられない（help の文字のみ）。
15. **通知の期限（表示期間）**: notification に表示期限・終了日が無い。「締切までの常設」が表現不可。
16. **section.columns / purpose / action.placement は出力に反映されない**（コンパイル規則）。2列配置や sticky を指定しても確認できない。
17. **view.states.loading は未対応**。
18. **gender 等の分類を表示する status の色割当**: variant は自由文字列で、値の列挙が分からず検証されない。
19. **取り下げの確認の理由入力**: 取り下げ理由を聞く入力ダイアログが作れない（confirm は message のみ）。
20. **2つのフロー間の遷移**: 「申込フロー」と「詳細→取り下げ」を別 flow として持てても、flow に属さない view（一覧/詳細）の steps 上の位置づけが書けない。
