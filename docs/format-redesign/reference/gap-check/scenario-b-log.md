# シナリオ B（小売チェーン在庫管理）決定ログ

検証: parseYamlV2 成功、全 view を renderViewV2 で描画し data-unknown-component なし。

## 1. ルールが沈黙していた点

### App 層
1. ロール別の通知出し分け。app.notifications に role が無い。決定: 夜間バッチ告知のみ app.notifications に置き、「棚卸し締切が近い」通知は通知にせず、本部管理者専用 view `deadline_alert`（role 指定）の list に代替した。欲しいルール: 「特定ロール向け通知は notifications ではなく role 付き view の note / 状態で表す」か、Notice に role を足す指針。
2. ロール別のナビ。navigation に role が無く、店舗担当者にも「本部管理」グループが見える。決定: group 名「本部管理」で示すだけ。欲しいルール: 「ロール専用 view は専用 group にまとめる」。
3. 2 ロールに対する header.userName。ログイン者は 1 人しか書けない。決定: 佐藤 花子 固定。ロール切替の見せ方の指針なし。
4. ロールを参照する書き方。flows.role / views.role は文字列 1 つで、app.roles と一致する必要があるのか、複数ロール共有（両ロール可）をどう書くか沈黙。決定: 共有 view は role を省略（= 全ロール可と解釈）。「role 省略 = 全ロール」を明文化してほしい。
5. navigation に入れる view の選定。商品詳細・確認・完了・ページ 2 などパラメータや途中状態を要する view をナビに入れるか。決定: 入れない（入口となる view のみ）。nav は同 group 内の入口 view 名を指定（product_detail の nav は stock_list、確認画面は入力画面）。
6. グループ数・項目数の目安がない（R-A03 は「多いとき」のみ）。決定: 2 group・各 3〜4 項目。

### Flow 層
7. 単一画面で完結する操作（商品編集、招待、ロール変更）を flow にするか。R-F01 は「複数画面」のみ。決定: flow 無し、同一 view の states.success で完了を伝える。flow 化の閾値を明文化してほしい。
8. 閲覧・検索系画面（ダッシュボード、在庫一覧）は flow に属さない。flow に入れない view の扱いが未記述。
9. 複数ページの棚卸し。ページングを flow の step で表すのか、1 view 内のページング機構があるのかが沈黙。決定: ページごとに view を分け（count_page1/2）、1 flow の step にし、入力→確認→完了の形を満たした。ただし「ページ」は業務上の step ではなく分割にすぎず、stepper 表示が冗長。欲しいルール: 「大量の同種入力は step ではなくページとして扱う」。
10. 棚卸しの「差異の確認」を確認 step に兼ねさせた。確認画面に差異だけを出す（全件ではなく）てよいか沈黙。
11. resumable: true にする基準。決定: 棚卸しと入出庫（長い手続き）で true、下書き保存を副アクションに置いた。

### View 層
12. ダッシュボードの KPI の表現。決定: kind: summary の Section に component: number + value（ラベルに単位を入れる）。単位表記・色・前日比などの指針なし。数値の `value` を number で書く規約も沈黙。
13. ダッシュボードの primaryAction。何も主にしなくてよいか、閲覧専用 view の主アクションの要否が沈黙。決定: 「在庫一覧を開く」を primary にした。
14. 一覧での一括操作（選択して「発注候補に追加」）。list.selection: multiple はあるが、選択行に対して実行する Action の書き方（kind: custom で view の primaryAction に置く）が沈黙。選択 0 件時の案内は R-V05 に従い states.error に書いた。
15. CSV ダウンロード。専用 kind が無く kind: custom の secondaryAction で表現。「ダウンロード系は custom + 動詞ラベル（〜をダウンロードする）」の指針を希望。
16. 一覧の primaryAction の選び方。R-V13 は「新規作成を主アクション」だが、在庫一覧に新規作成は無く、業務成果に直結する「発注候補に追加」を primary とした。R-V13 との優先関係が沈黙。
17. 詳細 view の編集・廃番。決定: 編集 = primaryAction（navigate）、廃番 = secondaryActions の style: danger + confirm(danger: true)。破壊的操作の置き場所（副アクションか、別 view か、展開 Section か）の指針が無い。
18. 破壊的操作の danger を R-V02/R-V03 のカウントにどう数えるか沈黙（secondary 3 個以内に danger を含めるか）。決定: 含めた。
19. ロールによるアクションの出し分け。「編集」「廃番」は本部管理者のみだが、共有 view の Action に role が無い。決定: 全員に見える形で書き、スキーマ上は区別できない（3 節参照）。「ロール専用 Action は専用 view に切り出す」指針があれば product_detail を 2 つに分けられた。
20. 詳細 view の layout。R-V11 は観点切替にタブを許すので tabs（基本情報／店舗別在庫／履歴）を選んだが、sectioned との選択基準が沈黙（R-V12 は「多く長い画面」）。
21. 閲覧専用 view（detail/ダッシュボード）の states。empty/loading を書く要否が沈黙。決定: 必要なところだけ。
22. 「戻る」系の副アクションを tertiary にする際の戻り先文言（「在庫一覧に戻る」）の定型が未記述（R-W02 は「戻る」の揺れ防止のみ）。「入力に戻る」と「前のページに戻る」を使い分けた。
23. 行アクション（rowActions）のラベル規則。決定: 「商品詳細を開く」「ロールを変更する」。R-W03 で足りるが、同一行の複数アクション数の上限は沈黙。
24. 再利用のための id 命名規則が無い。決定: view 名は snake_case の業務名詞（stock_list, product_edit, count_page1）、Section id は短い名詞（basic, lines, results）、Action id は動詞（save, cancel, back）。item は camelCase の業務名詞。
25. 1 view の Section 数の目安が無い。決定: 1〜3 個（編集画面は 3 個）。

### Section 層
26. 階層カテゴリ約 200 件。component の選択表（§5.1）は「選択肢が多く文字で絞り込みたい → combobox」までで、階層（パス）の表現が無い。決定: combobox + options に「飲料 > お茶」の ">" 区切りラベルを入れ、help に件数を記載（実データは 6 件のみ書いた）。多数件の options を YAML に何件まで書くか、外部参照の方法も沈黙。
27. 販売状態のオン/オフ + 保存ボタン。要件は「オン/オフ」だが §5.1 は「保存で確定 → checkbox」。決定: checkbox「この商品を販売する」。ルール通りだが、ラベルを肯定形にする規約は沈黙（「販売停止にする」ではなく肯定形にした）。
28. 商品画像。file + accept: image。複数枚か 1 枚か（photo_grid との使い分け）が沈黙。決定: 1 枚で file。
29. 「同一ラベルが複数ある」棚卸しの項目。repeatable は「行を追加する」前提で、既存商品を 1 行ずつ埋める固定行に不向き。決定: 商品ごとにフィールドを並べる（item は actualTea 等）。固定行の繰り返しの表現ルール無し。
30. 差異があるときだけ理由を必須にする。visibleWhen は equals のみで「実数 ≠ 帳簿」を計算できない。決定: 「差異がある」checkbox を補助項目として置き、true のとき理由 textarea を表示（required: true）。計算に依存する条件表示の書き方が沈黙。R-I13 の「参照先の help で予告」は help に記載。
31. 参照用の値（帳簿在庫）の見せ方。readonly 入力欄は R-I08 で避けるが、入力欄の隣に参考値を出す正規の方法が無い。決定: help に「帳簿上の在庫数は 36 です」と書いた。動的値・入力欄ごとの参考値の指針なし。
32. 一覧の絞り込み条件の数。要件の「商品名・SKU・店舗・在庫数・安全在庫・状態」6 軸に対し R-S09 は「少数」。決定: keyword（商品名・SKU）, 店舗, 状態の 3 つに集約し、在庫数・安全在庫は列の並べ替えに回した。
33. 一覧の search フラグと絞り込み Section の併用（list.search: false にした）。両方ある場合の役割分担が沈黙。担当者一覧は絞り込み Section 無しで search: true にした。
34. 詳細画面の「店舗別在庫のテーブル」「履歴タイムライン」の Section kind。テーブル = kind: list（R-S07）。タイムライン = kind: readonly の timeline フィールド。timeline の value の形式（文字列か配列か）、props の書き方がドキュメントに無く、文字列で書いた。
35. 一覧のサーバ側ページング／件数表示。pageSize の目安が沈黙（20 / 10 とした）。
36. Section の columns の既定。R-S13 は 1 を基本とするが、フィルタ 3 項目・明細 3 項目で 3 を使った（一組で読む項目と言えるかは主観）。
37. 夜間バッチ告知のような「補足」を note にするか通知にするか。R-A04/R-S12 から通知にした。
38. 確認画面の明細表示。kind: readonly に「明細1」「明細2」のように行を item 化したが、複数行の確認は list か readonly かが沈黙（repeatable の入力結果を確認画面でどう出すか）。

### Field 層
39. width の対応表。決定: 商品名・メール・商品選択・キーワード = lg、SKU・店舗 = md、単価 = sm、数量・安全在庫・実数 = xs。内容の桁数ごとの標準（例: 数量 xs、金額 sm）の対応表が R-I15 に無い。
40. 数量に最小値 1 を課す方法。top-level rules に min を書けるが、rules のキーの命名規則とメッセージの「＊」規則（R-I14 は props.error）との関係が沈黙。決定: rules.positiveQty に message を「＊…」で書いた。
41. 理由の radio（選択肢 5 個）。ルール通り radio にしたが、1 行 3 列の明細内に縦並びで置くと崩れるかの配慮は沈黙。
42. 文字数制限の書き方。R-I06 に従い label に「（50文字以内）」を入れたが、実際の最大長を validation に持たせる方法（max）との二重管理の扱いが沈黙。
43. 店舗の選択肢数。radio / select の閾値（5 / 6）が店舗数に依存する。決定: 一覧の絞り込みは「すべて」を含めて 6 個で select、入力は 6 個で select。「すべて」を選択肢数に数えるかが沈黙。
44. 状態フィルタ（すべて/適正/欠品間近/欠品 = 4）はサンプルで segmented 例があるが、R-§5.1 は radio。radio を採用。segmented をいつ使うかのルール無し。

### 文言
45. 夜間バッチ告知の文言。R-A05 に従い具体的に。実行中の影響まで書くかは任意。
46. 「CSV をダウンロードする」「発注候補に追加する」等の英字略語の混在（CSV）の可否が沈黙。
47. ボタンの「保存する」と「下書き保存」「ロールを変更する」の使い分け。R-W02 は同義は揃えると言うが、確定の保存と下書きの保存の区別が沈黙。

## 2. ルールが曖昧または矛盾していた点

1. R-V13（一覧は新規作成を主アクション）と R-V01（最も重要な 1 つを主に）。在庫一覧で重要なのは新規作成でなく一括操作。どちらを優先か。
2. R-F05 と R-S06/R-F06。廃番は取り消せない操作か。可逆（「販売状態をオフ」）ならば confirm は不要か、不可逆なら confirm か。廃番は不可逆と見なし confirm にした。
3. 「戻る・キャンセル・中止は tertiary 1 つまで」(R-V03) と複数ページ棚卸しの「前のページに戻る」「入力に戻る」。ページ戻りも tertiary か。決定: 前のページに戻る/入力に戻るは secondary、中止だけ tertiary。サンプル（order_confirm の「入力に戻る」= secondary）に合わせた。
4. R-V05（ボタンを無効化しない）と一括操作（選択 0 件のとき）。states.error は 1 view 1 メッセージで、押下時の案内だけを置き、バリデーション失敗（入力エラー）との共用になる。
5. R-I04「placeholder は使わない」と、スキーマ §Field の `example`「placeholder として使う」の記述が矛盾（実装では support text に描画される）。02-schema-v2.md の example 説明が古い。
6. §5.1「複数を選ぶ → checkbox + multiple」と、約 200 件の階層カテゴリのような多数の複数選択（該当なし、今回は単一選択）。多数かつ複数の場合の指針が無い。
7. toggle の定義（切り替えた瞬間に反映）と、要件の「オン/オフ」の語。ビジネス側が「オン/オフ」と呼ぶだけで即時反映ではない場合は checkbox、という判断を R-I 側で明記してほしい。
8. R-S02「1 Section の項目は目安 7 個以内」と、repeatable の明細内の項目数、棚卸しの Section（商品 ×3 項目で 9 個）。繰り返しの 1 行を 1 項目と数えるか。棚卸しは 6 個と 3 個にページ分けした。
9. R-S03（必須を折りたたまない）と、備考（任意）の collapsed。ルール上 OK だが、入出庫の備考を折りたたむ価値（R-S05「小さくするためだけに折りたたまない」）が微妙。
10. R-F03「自動変換した入力値は確認」と、棚卸しの確認が差異のみでよいか。
11. 02-schema-v2 の Section.visibleWhen の説明（表中: セクション全体を隠す / 変換規則: フィールド単位）が互いに矛盾して読める。今回は使わず回避した。
12. flow の steps と view の role。flow.role と view.role が異なる場合の優先関係が沈黙（本シナリオでは同一にした）。
13. R-V12 の「多く長い画面」の閾値と R-V11 の tabs 選択基準。同じ詳細画面に tabs と sectioned のどちらも当てはまる。
14. R-A04 は「処理結果は View の states に書く」とあるが、一覧の一括操作の結果（発注候補に追加した）を同じ view の states.success に置いたとき、画面再描画後の表示タイミングが不明。
15. kind: summary と kind: readonly の使い分けが規則に無い（KPI を summary とした。コンパイル規則では両方 definition_list）。

## 3. スキーマで表現できなかった点

1. 通知のロール限定（「本部管理者だけに見せる」棚卸し締切通知）。Notice に role/対象が無い。代替: 専用 view。
2. ナビ項目・Action・Section のロール限定。role は view / flow 単位のみ。「編集」「廃番にする」「担当者管理」を本部管理者のみにする表現が view 分割以外に無い。
3. 行アクション（rowActions）の confirm / style。「無効化」を一覧の行で危険操作として出せない。代替: ロール変更 view に無効化を置いた。かつ rowActions.to は未対応（コンパイル規則）。
4. 一括操作の対象（選択行）への紐づけ。選択中の行に作用する Action かどうか、選択数の表示が書けない。
5. CSV ダウンロードなど副作用の種類を示す kind（download）が無い。custom で代用。
6. 階層カテゴリ（ツリー）選択と大量 options の外部参照。combobox の options は静的列挙のみ。200 件をどう与えるかが無い。
7. 商品検索（検索して選ぶ）の非同期検索。combobox は静的な候補絞り込みのみ。
8. 入力値の計算に基づく条件（実数 − 帳簿 ≠ 0 で理由を必須）。visibleWhen は equals のみ。
9. 棚卸しのページング（同一 view 内で複数ページ・全体進捗）と、行ごとの固定項目（商品名・帳簿数は表示、実数だけ入力）の表の中の入力。list は入力セルを持てない。
10. 1 行の表示と入力が混在するテーブル（帳簿数 + 実数入力 + 差異理由）。
11. KPI カード（数値 + 単位 + 比較）。単位は label に埋め込み。summary は definition_list にコンパイルされ、強調表示や色がない。
12. timeline の項目データ（日時・種別・内容）の構造。value に文字列で逃した。
13. ダッシュボードの一覧と KPI の連動（KPI をクリックして在庫一覧に絞り込み遷移）。navigate に絞り込み条件を渡せない。
14. 商品詳細へのパラメータ付き遷移（どの商品か）。navigate.to は view 名のみで、対象 ID を渡せない。同様に product_edit への遷移も対象不明。
15. ステータスの色／variant の enum が schema にない（variant は自由文字列）。
16. 夜間バッチ中の動作変化（在庫数の更新停止）など、システム状態に連動した表示。
17. 担当者の招待の送信結果や、無効化後の一覧反映。success 文言のみで状態遷移は静的。
18. 複数の画面にまたがる共通の選択店舗（コンテキスト）。header.tenantName は店舗でなくテナント。
