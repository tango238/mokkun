## デザインシステムの前提と原則

### 目的・位置づけ
- DADSは、スタイリングの考え方を提供するデザイン言語、情報の視覚表現とインタラクションを具現化するUIコンポーネント、ユーザビリティとアクセシビリティを踏まえた設計・実装のためのガイドラインから構成されるデザインアセットである。
- デジタル庁のミッション「誰一人取り残されない、人に優しいデジタル化を。」の実現に寄与することを標榜している。
- 官公庁や地方自治体などの行政機関や公共性の高い組織等のウェブサイト／ウェブアプリケーション／オンラインサービスまたはシステム等での利用を念頭に構築されている。
- 「β版」はリビングスタンダードであることを示し、継続的改善の意志を込めた表示である。
- 構成は、デザインシステム本体（ウェブサイト）、デザインデータ（Figma）、コードスニペット（HTML版／React版、GitHubとStorybook）、イラストレーション・アイコン素材である。
- デザインシステムとは「ウェブサイトやウェブアプリケーションを作る際に参照するルールのまとまり」である。
- DADSは準拠のための規約やデザインを機械的に生成するルールではなく、デザインの考え方や枠組みとアクセシビリティを掛け合わせた「仕組み」である。
- 行政機関か否かを問わず誰でも無料で利用できる。

### 理念（デザイン原則）
- **アクセシビリティファースト**: アクセシビリティを最優先事項に位置付け、WCAG等のガイドラインを最大限に取り込む。
- **行政機関にとって高い汎用性と利便性**: 特定のブランドやサービスのためではなく、プリミティブな情報要素の組み合わせでコンポーネントを形づくることで汎用性を保ち、サービスごとのスタイルガイドを矛盾なく作成できるようにする。
- **継続的かつ持続可能な改善活動および研究と実践**: 最新の規格やドラフト段階の仕様を研究・実践し、用途やニーズの変容に寄り添う。
- 一般的なデザインシステムの特徴として、一貫性のある情報コンポーネントによる学習効率・開発効率の向上、記憶容易性・エラー回避率・利用満足度の向上も包含する。

### 想定利用者
- 特にデザイナー（ウェブデザイナー）、開発者（ソフトウェアエンジニア・フロントエンドエンジニア）、ウェブサイトの企画・情報設計の担当者の利用を想定している。
- 調達仕様書の策定担当者は、デザインシステムの使用を要件や検収要件に掲げることで事業者にガバナンスを提供できる。
- デザインシステムを活用してもデザイン作業やデザイナーが不要になることはない。

### ロール別の使い方
- デザイナーは、ガイドラインを理解する（特にアクセシビリティの記述は最優先事項として扱う）→アセットを活用する→ローカルデザインシステムを作る、という要点を踏まえる。
- フロントエンドエンジニアは、標準化されたコンポーネントを再利用し、HTML/CSS/JavaScriptまたはReact/Tailwind CSSのコードスニペットを利用する。
- プランナー／インフォメーションアーキテクトは、情報設計からワイヤーフレーム設計まで一貫した情報粒度でUIモデリング・テンプレート設計を行える。
- 運用責任者・組織内の全関係者は、DADSを使うことでアクセシビリティ確保の下地を得られるが、アクセシビリティを踏まえた運用設計も必要である。

### サービスへの適用方法（ローカルデザインシステム）
- DADSはプラットフォーム型デザインシステムであり、固有の組織に依拠したブランド概念を備えないため、使用にあたってはローカルデザインシステム（導入先専用のスタイルガイド）の作成が前提となる。
- DADSを導入先で直接使うのではなく、DADSをベースに導入先専用のデザインシステムを定義してから使う。
- Figmaデータ・コードスニペットに適用済みのデザイントークン（カラー、書体の大きさ、角の形状、余白など）はデジタル庁ウェブサイトをベースとした初期値であり、特定の外観を規定するものではなく編集の起点である。
- 変更する必要がない項目はDADSの初期値をそのまま使用して構わない。
- 編集できる範囲は、カラー（キーカラーの選択／ブランドカラーでの上書き、ニュートラル以外の共通カラー作成、セマンティックカラーの明度・彩度調整）、タイポグラフィ（書体の大きさ・行高の追加・変更）、余白（基準単位と倍率スケールの設定）、角の形状（コンポーネント単位の角丸値、5段階は目安）、エレベーション（必要な高さレベルと高低差）、リンクテキスト（リンクカラーの選定、青以外も禁止されない）、レイアウト（カラム割りの変更、ブレークポイント数の設定）である。
- 編集はDADSが備えるアクセシビリティの骨格を維持する範囲で実施しなければならない。
- 作成手順は、ブランドやコミュニケーション方針の規定を最初に定め、次にスタイル定義を更新し、最後にUIコンポーネントを調整する順序である。
- 手順例: (1) Figmaデータ取得 → (2) ファイル名・カバー・バージョンを導入先向けに変更 → (3) キーカラーをブランドカラーに置き換え → (4) 使用するコンポーネントを選定 → (5) コンポーネント単位で角の形状や余白を調整 → (6) 使用頻度の高いボタンのラベル等を入力済みのコンポーネントとして定義（作業効率向上と文言の揺れ防止）→ (7) 組み合わせが定まっているコンポーネントのセット（例: ラベル＋「※必須」＋サポートテキスト＋インプットテキスト＋「申請する」ボタン）を定義する。
- 上記と並行して画面仕様書（ワイヤーフレーム等）を作成し、定義済みコンポーネントで画面を構成し、調整点はコンポーネント定義に反映する。
- DADSのプリミティブな定義で足りない場合は、DADSの枠組みの中で独自の定義を追記する。
- Figmaコンポーネントの構成は維持する必要はなく、合わない場合は detach して組み直し、改めてコンポーネントとして定義できる。
- コードスニペットは環境に合わせて書き換えてよいが、WAI-ARIAの指定や強制カラーモード対応などアクセシビリティのための実装は取り除いてはならない。

## レイアウト

### 基本の考え方
- ページのレイアウトは文書構造上の要素を画面内のどこにどのように配置するかという設計である。
- サイト全体の情報構造から文書構造のパターンを抽出してレイアウトをテンプレート化することがある。
- 一貫性のあるレイアウトは学習効率を高め、ページの閲覧やサイト内の回遊を促進する。

### グリッドシステム
- グリッドシステムはマージン、カラム、ガターなどでレイアウトの基準となるスペースを定義する。
- 基本グリッドとして「1カラム」「12カラム」「左メニュー配置に12カラム」の3種が示されている。
- マージンはカラム全体とページの余白を設定してグリッドの配置を決め、ページ幅が狭くなった場合も想定して確保する。
- カラムの幅は本文の文字サイズの整数倍とする。
- 12列のフレームワークは柔軟性と分割・結合の容易さから一般的である。
- ガターは原則として本文の文字サイズの2倍を確保する（狭すぎると隣のカラムとの誤読の可能性が増すため）。
- システムなどでは左サイドにメニューやナビゲーションの領域を確保し、その領域は固定幅または可変幅とし、メニューの右端からマージンを設定してグリッドを形成する。

### カラム割り（12カラムグリッド上の例）
- 1カラムレイアウト: グリッドの全幅。
- 2カラムレイアウト: 9+3、3+9、8+4、4+8、6+6。
- 3カラムレイアウト: 3+6+3、4+4+4。
- 4カラムレイアウト: 3+3+3+3。
- カラムオフセット: 記事や読み物など、伝えたい内容にフォーカスさせるために使う（例: 8カラム幅＋左2カラムオフセット、6カラム幅＋左3カラムオフセット）。

### ブレークポイント
- DADSはブレークポイントを1つ設定する想定で、作例ではデスクトップ向けとそれ以外（モバイルデバイス等）向けの2つのレイアウトを提供する。
- 設定例はモバイル・タブレットが768px未満、デスクトップが768px以上である。
- 一般にはタブレット向けや大型デスクトップ向けなどで2つ以上設定することもある。

### アクセシビリティ上のレイアウト規則
- リキッドレイアウト（可変レイアウト）を採用する。
- グリッドではカラムまたはガターのどちらかを可変幅、もう一方を固定幅としてリキッドレイアウトを実現する。
- リキッドレイアウトでも横スクロールが発生する場合は、横スクロールバーを隠さない。
- 視覚的な要素の配置と読み上げ順序をできるだけ一致させる（CSSで並べ替えても読み上げ順序やTabフォーカス順序は変わらない）。
- CSSグリッドの `order` と `grid-placement` は論理的な並び替えではなく視覚的な並び替えのみに使用する。
- DOMの順序から大きく外れた位置変更を行う場合は、文書構造の並び順そのものの変更を検討する。
- 関連達成基準: 1.4.4 テキストのサイズ変更（AA）、1.4.8 視覚的提示（AAA）、1.4.10 リフロー（AA）、1.3.2 意味をなすシーケンス（A）、2.4.3 フォーカス順序（A）。

### 行長
- テキストブロックのグリフ幅は半角80文字（全角40文字）程度を目安とする（詳細は「タイポグラフィ」参照）。

### 原文に記載がない項目
- コンテンツ最大幅（px値）、マージン・ガターの具体的なpx値、カラム数のブレークポイント別切り替え（例: モバイル時のカラム数）は記載なし。
- header / main / footer の並び順、グローバルナビゲーションやパンくずの配置位置といったページ構造の規定は、これらのファイルには記載なし（コンポーネント側のページ、例: `components/breadcrumb/`, `components/header-container/` にある可能性）。

## 余白

### 余白の機能と種類
- 適切な余白はコンテンツの過密感を防ぎ可読性を向上させる。
- 余白に一定のルールを持たせることで要素間の関係を強調し、明確な視覚的階層を確立する。
- 余白を形成する要素にはパディング、マージン、行間隔、空白（ホワイトスペース）がある。
- 縦方向に並ぶボックスの隣接する上下マージンは相殺される（float と position: absolute を除く）。

### 余白ルールの考え方
- 同種の要素には同じ間隔値を使用する。
- 間隔値に絶対的な数値はないが、使用する間隔値に規則性を与えることが非常に重要である（モジュラースケールや比率を用いることが多い）。
- 重要な要素にはより大きな間隔値、重要でない要素にはより小さな間隔値を与える。
- 要素間に十分なスペースを確保し、密集・詰まった感じをできる限り回避する。
- レスポンシブデザインではビューポートごとに間隔が適切にスケーリングされることを確認する。

### 余白スケール
- 余白ルールは基準となる余白の単位を選定し、その倍率スケールからルールの範囲を決める。
- 一般的に利用されることの多い基準単位は8 CSS pxである。
- スタイルガイドで定義される余白スケールは3つから5つ程度になることが多い。
- 余白は通常コンポーネントやテンプレートに定義済みのため、余白を単体で配置することはない。
- 余白スケールのトークン化は必要に応じて実施する。
- 適用例: 基準単位の等倍8 CSS px、3倍24 CSS px、8倍64 CSS pxの3つの余白スケールを使う。
- 適用例の配置: 上方のブロックとの間に64 CSS px、カテゴリーの上に24 CSS px、カテゴリーとセクションタイトルの間に8 CSS px、タイトルと本文の間に24 CSS px。

### 関係性と階層の明示（縦のリズム）
- 関連性の高い要素には小さな余白、関連性の低い要素には大きな余白を与えて文書構造を強調する（例: 画像とキャプションの間は、キャプションと本文の間より小さくする）。
- トップレベルの見出しほど周囲に多くの余白を与え、階層が下がるにつれて見出しに与える余白を減らす。
- それぞれの見出しのフォントサイズに見合う大きさの余白を配置する（見出しの階層が進むごとに見出しと本文の間の余白も縮まる）。
- 段落と段落の間は行ボックスの高さの1.5倍以上（フォントサイズの2.25倍以上）とする（タイポグラフィのアクセシビリティより）。

### アクセシビリティ
- 空白（`word-spacing`、`letter-spacing`、`text-align: justify`）や両端揃えを使って文字の表示位置やレイアウトを調整しない。
- 全角スペースや `&nbsp;` で文字位置をそろえない（スクリーンリーダーの読み上げに支障をきたす）。
- 表組のセル内や定義リストの見出し等での両端揃えにも注意する。
- 余白は使用する間隔値に規則性を与え、インタラクティブ要素のターゲットサイズを確保する（ローカルDS編集後も満たす要件）。
- 余白を詰めたことでターゲットサイズが規定値を下回ることは許容されない。

### 原文に記載がない項目
- フォームフィールド間、フィールドとボタン間、ボタン同士の間隔の具体値は記載なし（コンポーネント側の可能性）。

## タイポグラフィ

### フォント
- 書体は可読性・視認性が高いサンセリフとし、「Noto Sans JP」と等幅フォント「Noto Sans Mono」を採用する（SIL Open Font License 1.1）。
- OSやデバイスネイティブのシステムフォントの使用を制限するものではない。
- ユーザーエージェントによって表示フォントが変更されうる前提で、情報伝達は書体に非依存で実施可能にする。
- 太さレベルは「N」= 400（normal）と「B」= 700（bold）の2つである。

### 書体の大きさ
- 48〜64 CSS px: 視覚的なインパクトが必要なデザイン要素としての文字サイズ。
- 16〜45 CSS px: 読み物コンテンツの見出しや本文を構成する文字サイズ。
- 本文やUIにおいては16 CSS px以上が基準値である。
- 14 CSS px: 基本的には使用せず、フッター要素などコンテンツに付随する情報や領域的な制約がある場合のみ使用する。
- 14 CSS px未満の大きさの使用は原則として許容されない。
- 要素に応じて割り当てる書体の大きさは、ウェブサイト内で一貫性を保つ。

### 行高
- 読み物コンテンツにおける本文テキストの行高はフォントサイズの少なくとも1.5倍を維持することを推奨する。
- 見出しなど文字サイズが大きいものは本文よりも行間を狭めたほうが可読性が維持される。
- 管理画面や業務用システムなど表示情報量を優先する場合は行間をかなり狭めることがある。
- 行高の定義: 100%（ボタン等のワンライン）、120%（管理画面等で情報量を最優先）、130%（管理画面等で情報量を優先）、140%（見出しなどやや大きな文字）、150%（一般的な本文・見出し、本文の行間として最低限度）、160%（一般的な本文）、170%（心理的負荷の軽減を考慮した本文）、175%（同、グリッド幅やフォントサイズに応じ170%と使い分け）。
- Figmaでは%表記だが、CSSではnumber（単位なし数値）で実装する。

### テキストスタイル（トークン名は「種別-サイズ太さ-行高」例: Std-17N-170）
- **Display (Dsp)**: ページのトップ領域のヘッドコピーなど視覚的インパクト用で、64／57／48 px、行高はすべて140%、letter-spacingは0。
- **Standard (Std)**: 見出しや本文など最も使用される普遍的なスタイルで、45（140%, 0）、36（140%, 1%）、32（150%, 1%）、28（150%, 1%）、26／24／22／20（150%, 2%）、18（160%, 2%）、17（170%, 2%）、16（170%, 2%）、16（175%, 2%）の各N/Bがある。
- 見出しは常に本文との違いが視覚的に明確になるように設定する。
- 視認性・可読性の観点から基本的にフォントサイズは16 CSS px以上で使用する。
- **Dense (Dns)**: 管理画面や業務システム、データテーブル内など表示情報量優先で、17／16／14 px × 行高130%／120%、letter-spacingは0。
- **Oneline (Oln)**: 1行展開を前提としたUI要素向けで、17／16／14 px、行高はすべて100%、letter-spacingは2%。
- **Mono**: コード系コンテンツ向けで、17／16／14 px、行高はすべて150%、letter-spacingは0。

### その他の書式
- 日本語フォントに対するイタリックの使用は、そうしなければならない理由がある場合を除いて避ける。
- 長い範囲のイタリック体（斜体）は避け、日本語でのイタリック体の使用は最小限にとどめる。
- プリミティブなHTML要素のデフォルトのテキスト装飾を変更・取り消すことは推奨されない（必要な場合は十分にテストする）。
- 下線はリンクテキストを色のみで表現することを避けるために重要なテキスト装飾である。
- テキスト装飾のスタイル・色・太さのパターンを多数混在させない。

### 行長・可読性（アクセシビリティ）
- テキストブロックのグリフ幅は半角80文字（全角40文字）程度を目安とする。
- この目安を適用すべきかはコンテンツごとに判断する（例: 緊急時バナーは目安の制約を受けない）。
- 読みやすさの工夫（リキッド／レスポンシブ、冒頭の短い概要、予想読了時間・文字数表示、ページ内目次、見出し・段落・箇条書き・挿絵の適切な使用、続きから読みやすい配慮）が複数実装されている場合は、目安を超える幅でも構わない。
- 行ボックスの高さをフォントサイズの1.5倍以上、段落と段落の間を行ボックスの高さの1.5倍以上（フォントサイズの2.25倍以上）にする。
- テキストサイズが変更されても（200%以上の拡大を含む）ページの読みやすさや機能が変わらないようにする。
- フォントを変更させないことを企図して文字画像を使ってはならない（ロゴタイプを除く）。
- 関連達成基準: 1.4.4（AA）、1.4.8（AAA）、1.4.12 テキストの間隔（AA）。

- h1〜h6 の各レベルに対応するテキストスタイルの割り当て表は記載なし。
- 項目ラベル・サポートテキスト・エラーメッセージ用のテキストスタイル指定は記載なし（コンポーネント側の可能性）。

## リンクテキストと文言

### リンクテキストの表現
- リンクテキストは通常のテキストとは異なる色と、下線やその他の視覚的な手段を組み合わせて、通常のテキストから明確に区別できるようにする。
- 色情報が欠落してもリンクとわかるように、必ず色以外のテキスト装飾等（下線が最も一般的、ほかにビュレットや矢印等のリンクマーク）と組み合わせる。
- リンクカラーは簡単に区別でき、コントラスト要件を満たし、ウェブサイト内で一貫性をもつことが最も重要で、色覚多様性も考慮する。
- 慣習として未訪問を青、訪問済みをマゼンタ（紫）とするのが最も一般的である。
- 青以外の色相をリンクカラーにすることは禁止されないが、その場合はコントラスト要件・色覚多様性のほか、迷いなくリンクと認識できるよう配慮する。
- 内部リンク／外部リンクの境界はドメインだけでなくウェブサイトごとのポリシーに依存する。

### ステート
- Visitedには未訪問と明瞭に区別できるリンクカラーを設定する。
- Hoverはリンクカラー、下線、背景色の変更などサイト全体のトーン＆マナーに相応しい表現を選ぶ。
- Hoverで文字の太さや大きさを変化させるのは、文字領域のサイズ変化が他の要素に影響を与えない場合のみとする。
- Focus時は黒の外枠線と黄色の背景が付く（図示）。

### 新規タブ・ウェブページ以外へのリンク
- 新規タブ（新規ウィンドウ）を開くリンクには、リンクテキスト末尾にアイコンを配置してその旨を喚起する。
- どのリンクを新規タブで開くかはサイトごとのポリシーで決める。
- 末尾のアイコンには下線はひかれないが、クリッカブルエリアには含まれる。
- 新規タブで開くことを示すアイコンには「新しいタブを開きます」等の代替テキストを付与する。
- PDFやダウンロードファイル等へのリンクは、リンクテキストにファイル形式や容量（例:「（PDF:100KB、内閣府）」）を明記すると分かりやすい。
- ファイル形式をアイコンで示す場合も代替テキストが必要である。

### リンクの文言
- リンク先の情報を具体的に判断可能なテキストをリンクテキスト自体とする。
- 判断の目安は、リンク先のページタイトル（`<title>`）またはページの主題（`<h1>`）そのものであること、ページ内でユニークな文字列であること、目的がわかる十分な長さがあること、前後の文章からリンク先がわかること、のいずれかに文脈的に自然に該当することである。
- 「ここ」や「こちら」だけをリンクテキストにしない（例:「資料のダウンロードフォームはこちら」なら「資料のダウンロードフォーム」または文全体をリンクにする）。
- 記事一覧で「もっと詳しく」「詳細を読む」を並べるのではなく、記事タイトル自体をリンクテキストにする。
- やむを得ずユニークでない文字列をリンクにする場合は `aria-label` 属性で区別できるようにする。

### ターゲットサイズ
- リンクテキストは、インラインの隣接ターゲットと重複がない状態で少なくとも24×24 CSS px以上を目安とする。
- リンク領域の高さが16 CSS pxなど24 CSS pxに満たない場合でも、上下に4 CSS pxずつ隣接する余白があればターゲットサイズは確保されたとみなされる。
- 関連達成基準: 2.4.4 リンクの目的（文脈内）（A）、2.4.9 リンクの目的（リンクだけ）（AAA）、2.5.8 ターゲットのサイズ（最低限）（AA）。

### ボタン・その他の文言
- 使用頻度の高いボタンのラベル（例:「キャンセル」「戻る」「申請する」）はあらかじめ入力した状態でコンポーネントとして定義し、文言の揺れを防ぐ。
- ボタンのアクセシビリティについて「ボタンのフォーカス順序と表示順序に気をつける」がコンポーネント側で参照されている。

### 原文に記載がない項目
- ボタンとリンクの使い分け（ナビゲーションはリンク、操作はボタン等）の規定はこれらのファイルには記載なし（`components/button/` 側の可能性）。
- 一般的な文言・ライティングガイド（敬体、用語統一など）は記載なし。

## 色とアイコン

### キーカラー
- キーカラーは同じ色相の階調から選択し、プライマリー、セカンダリー、ターシャリー、バックグラウンドを含む。
- プライマリーカラーはサイトのトーン＆マナーを確定し、ロゴタイプ、ヘッダーやグローバルナビゲーション、CTAボタン、アクティブな状態表示など優先される動線や状況を示すUIに使用する。
- プライマリーカラーは主要な背景色とのコントラスト比4.5:1以上を維持できる色を選ぶ。
- 複数のプライマリーカラーを設定でき、その場合はそれぞれの色相・明度でセカンダリー／ターシャリー／バックグラウンドを展開する。
- セカンダリーカラーは副次的な動線や状況を示すUI（選択肢を提供するボタン、機能や状態を表示するパーツ等）に使い、プライマリーと同じ色相で明度が高いまたは低いものを選ぶ。
- ターシャリーカラーはセカンダリーと反対の明度で設定する。
- セカンダリー／ターシャリーは、背景と隣接する表示要素に使う場合は3:1以上、テキストに使う場合は4.5:1以上とする。
- 白・黒以外のバックグラウンドカラー上では、テキストや非テキスト要素のコントラスト比を調整する。
- キーカラー例: Blue、Green、Neutral、Light Blue、Cyan、Orange、Purple。

### 共通カラー（ニュートラル）
- 共通カラーは白〜黒のグレー階調をベースに、ページ共通要素、テキスト、境界線、背景、UIパーツに使用する。
- テキストと背景色のコントラスト比は常に4.5:1以上を保つ。
- 枠線やディバイダーなどの非テキスト要素は隣接する背景色と3:1以上を保つ。
- 白（#FFFFFF）背景では Gray-420 より暗いグレーが非テキスト要件（3:1）を、Gray-536 より暗いグレーがテキスト要件（4.5:1）を満たす。
- 黒（#000000）背景では Gray-600 より明るいグレーが非テキスト要件（3:1）を、Gray-536 より明るいグレーがテキスト要件（4.5:1）を満たす。
- プリミティブカラーは Blue／Light Blue／Cyan／Green／Lime／Yellow／Orange／Red／Magenta／Purple の各13階調、グレーは10階調（Solid Gray と Opacity Gray）である。

### 機能カラー
- リンクカラーはコントラスト比4.5:1以上を確保しつつ青（Default）と紫（Visited）を使い、紫には少し赤みを足して青との明度差を作り識別性を高める。
- フォーカスカラーは Yellow-300 と Black の2重構造であり、いかなる場合も変更してはいけない。
- 検索ハイライトカラーはシアンまたはマゼンタから選ぶ。
- ボタンなどのステートカラー（Default／Hover／Active）はキーカラーを反映して決め、ウェブサイト内で一貫性を保つ。

### アクセントカラー
- アクセントカラーは特定の要素に注意を引くため、多用されない程度に使用する。
- 装飾以外の用途や機能を持つコンポーネントに使う場合は、テキストで4.5:1以上、非テキストで3:1以上を確保する。

### セマンティックカラー
- セマンティックカラーはデザインスタイルやUI種別を問わず特定の意味が割り当てられた色で、一貫性のある視覚的な共通言語となる。
- **サクセス（Success）**: 成功、安全、完了などを意味する（緑、サクセス1／2）。
- **エラー（Error）**: 失敗やエラーのほか、危険情報や制約条件の提示など注意喚起を意味する（赤、エラー1／2）。
- **警告（Warning）**: 警告や禁止事項などを意味する（黄色系・オレンジ系、ワーニング1／2）。
- アイコンや枠線など非テキストに使う場合は背景色と3:1以上、テキストに使う場合は4.5:1以上が求められる。
- 色相を保ちさえすれば明度・彩度は調整できるが、セマンティクスの色相と意味の結びつきは変更しない（エラーを緑で示すことはできない）。
- 背景色が白または黒以外の場合は必ずコントラスト比を確認する。
- 「Primary」はセマンティックカラーではなくキーカラーの一種として定義されている（Info 等のセマンティックカラーは定義なし）。

### ブランドカラーとの関係
- ブランドカラーが4.5:1未満の場合は、同じ色相で明度を調整するなどしてキーカラーを決める。
- ブランドカラーはロゴや純粋な装飾に使い、各キーカラーはコントラスト要件を満たす相性の良い色を選ぶ方法もある。
- ウェブサイト内のすべての色遣いをブランドカラーの色相だけで構成する必要はない。

### アイコン
- アイコンは文書構造上の位置ごとに4種類定義される: ブロックレベルボックスの先頭＝フロントアイコン、末尾＝エンドアイコン、行ボックスの先頭＝リードアイコン、末尾＝テールアイコン。
- リードアイコン・テールアイコンは原則としてテキストシーケンスの一部となる（レイアウトによってはフレックスボックスとして並列に扱う）。
- アクセシビリティおよび適切な情報伝達の観点から、アイコンは必ずラベルと組み合わせて使用する。
- ラベルと組み合わせたアイコンには代替テキストは不要で、`<img>` は `alt=""`、CSSで配置する場合は何も指定しない（アイコンのために `aria-label` をつけない）。
- ラベルがリンクの場合はアイコンもリンク範囲に含め、アイコンとラベルを別の `<a>` 要素にしない。
- やむを得ずアイコン単体で使う場合は、本来のラベルの内容を代替テキストに設定する。
- アイコン単体がアクションやリンクをともなう場合は44×44 CSS px以上のターゲットサイズを確保する。
- DADSには、アイコン単体で配置しなければならないボタン用に、ラベルをアイコンの一部に含めた専用アイコンが定義されている。
- アイコンの色は背景色に対してコントラスト比4.5:1以上を確保する（非テキスト要素としてしか使わないことが保証されている場合に限り3:1以上でよい）。
- ローカルDSでの外観調整でも、アイコンがラベルと組み合わさる構成を維持する。

### 角の形状・エレベーション（補足）
- 角の形状は5段階（角丸なし0、スモール8、ミディアム16（横長12）、ラージ32（横長16）、フル＝高さまたは幅の50%、数値は図の代替テキストより）を目安にコンポーネント単位で規定する。
- 大きさや縦横比により同じスタイルでも見え方が異なるため、コンポーネントごとに角丸半径を調整して視覚的な統一感を保つ。
- 角の形状を変えることで特定の図形を強調できる。
- エレベーションのデフォルトは高さレベル0で、ほとんどの要素はレベル0であり、レベルに応じて Style 1〜8 のドロップシャドウを適用する。
- オーバーレイ表示されるコンポーネント（ダイアログ等）は下にあるものより少なくとも2段階上（レベル0のみなら2、レベル1のボタンがあれば3以上）とする。
- Hover時に高さを変えるコンポーネントは設置レベルより少なくとも1レベル以上の高さを確保する。
- システムや管理画面など過密なUIでは高低差を狭くして視覚表現を最小限にする。
- 過度なエレベーション定義は避け、高低差で理解が容易になるUI構造の場合にだけ設定する。
- オーバーレイシェードはモーダル表示時に親要素への視線と操作を遮断し、高さレベルを0にリセットし、モードレスダイアログでは使用できない。
- オーバーレイシェード自体は原則クリッカブル（フォーカス可能）ではなく、オーバーレイ側にモード解除のトリガーを用意する。

- 参照基準は WCAG（最新2.2、2.0 は JIS X 8341-3:2016 と互換）および WAI-ARIA 等の国際的な勧告である。

- DADSが特に注意を払う項目は、色の組み合わせとコントラスト比、フォントサイズ、キーボード操作とフォーカスインジケーター、リンクやボタン等のターゲットサイズ、操作に対応したインタラクション表現、動きのあるオブジェクトの扱い、大きさの可変や内容量の増減を踏まえた外観構造である。

- ローカルDSでの編集はアクセシビリティの骨格を維持する範囲で実施しなければならない。

### コントラスト
- DADSでは「サイズの大きなテキスト」の緩和規定を除外し、サイズに関わらずテキストおよび文字画像は背景色に対して4.5:1以上を確保する。
- UIコンポーネントおよびグラフィカルオブジェクトは隣接色との間で3:1以上を確保する（1.4.11）。
- フォーカスインジケーター自体も非テキストとして背景色や隣接色と3:1以上が求められる。
- disabled 状態のUIのテキストや非選択時の placeholder テキストはコントラスト要件の対象外である。
- 高さを持つ要素は置かれる面に対して3:1以上が必要で、ドロップシャドウではコントラスト比を確保できないため要素にボーダーを持たせる。
- オーバーレイシェード上に表示される要素にも必ずボーダーをつける（強制カラーモードで境界が消えるのを防ぐ、透明のボーダーでも可）。
- テキストのカラーを指定したら、そのテキストが配置されうるすべての要素の背景色も合わせて指定する。
- グラフ等でメモリ線が3:1を満たさない場合は、近くに4.5:1以上のテキストを配置するか、説明テキストを代替コンテンツとして用意する。

### 色だけに依存しない
- 色だけで情報を区別しない（1.4.1 色の用途）。
- リンクは色以外のテキスト装飾（下線等）と必ず組み合わせる。
- カラーユニバーサルデザイン推奨配色セットを参考にキーカラー等のパレットを選定する。

### キーボード・フォーカス
- フォーカスインジケーター（外側黒・内側黄色の二重線、Yellow-300 と Black）は変更してはならない。
- 視覚的な配置と読み上げ順序・Tabフォーカス順序をできるだけ一致させ、CSSの `order` や `grid-placement` は視覚的並び替えのみに使う（1.3.2、2.4.3）。
- 強制カラーモードでも要素の境界や状態を判別できる実装（コードスニペットのサンプル）に従う。
- オーバーレイシェードに覆われた要素は操作できず、オーバーレイ内にモードを解除するトリガーを用意する。

### ターゲットサイズ
- リンクテキスト等は隣接ターゲットと重複なく少なくとも24×24 CSS px以上を目安とする（上下4 CSS pxずつの余白があれば16 CSS px高でも可）（2.5.8）。
- アイコン単体でアクションやリンクをともなう場合は44×44 CSS px以上を確保する。
- ラベルとのコントラスト比や余白を詰めた結果ターゲットサイズが規定値を下回ることは許容されない。

### ラベル・代替テキスト
- アイコンは必ずラベルと組み合わせ、組み合わせたアイコンの代替テキストは空にする。
- アイコン単体の場合は本来のラベル内容を代替テキストにする。
- 新規タブアイコンやファイル形式アイコンには代替テキストを付与する。
- リンクテキストはリンク先を具体的に判断できる文言にし、ユニークでない場合は `aria-label` で区別する。

### テキストの拡大・リフロー
- リキッドレイアウトを採用し、横スクロールが発生する場合もスクロールバーを隠さない（1.4.4、1.4.10）。
- テキストサイズを200%以上に拡大しても読みやすさや機能が変わらないようにする。
- 本文やUIは16 CSS px以上、14 CSS px未満は原則不可とする。
- 読み物の本文の行高はフォントサイズの1.5倍以上、段落間はフォントサイズの2.25倍以上にする。
- 文字画像を使わない（ロゴタイプを除く）。
- 空白文字や両端揃えでレイアウトを調整しない。

### 見出し構造
- 見出しは常に本文との違いが視覚的に明確になるようにし、階層に応じたサイズと余白で情報の階層構造を視覚的にも構成する。
- （DADSサイトの方針ページでは、Storybookの各ストーリーにH1見出しが存在しないこと、表で `th` を `td` でマークアップしていること、テキストフィールドやスピンボタンにラベルがないことを 1.3.1 の不適合として挙げており、裏返せば各ページH1・適切な表見出し・フォームコントロールのラベルが必要とされている。）

### 原文に記載がない項目
- フォームのエラー識別・エラーメッセージの表示方法、必須表示の方法、ラベルとフィールドの配置規則は、これらのファイルには具体的な記載なし（ローカルDSの作成手順例で「ラベル＋※必須＋サポートテキスト＋インプットテキスト＋ボタン」の縦並びセットが図示されるのみ）。
- 見出しレベル（h1〜h6）の使い方の規定は記載なし。
- エレベーションの Light Dismiss 操作は「モーダルダイアログのガイドラインに記述予定」となっており未記載。

## 横断的に繰り返される原則

- アクセシビリティは最優先事項であり、デザイン調整・ローカルDS化のどの段階でもその骨格（コントラスト、ターゲットサイズ、フォーカスインジケーター、強制カラーモード対応、ARIA）を崩してはならない。
- コントラスト比の基準はテキスト4.5:1以上、非テキスト（枠線、ディバイダー、アイコン、高さを持つ要素、フォーカスインジケーター）3:1以上で、全ページで一貫して繰り返される。
- 色だけで情報を伝えず、リンクの下線、アイコンとラベルの併記、ボーダーなど色以外の手段と必ず組み合わせる。
- アイコンは必ずテキストラベルと組み合わせ、単体使用は例外として代替テキストと十分なターゲットサイズ（44×44 CSS px）で補う。
- 規則性と一貫性: 同種の要素には同じ値（余白、文字サイズ、ステート表現、リンクカラー、角丸）を用い、ウェブサイト内で一貫させる。
- 少数のスケールで定義する: 余白は基準8 CSS pxの倍率で3〜5段階、文字サイズは定義済みテキストスタイル、角丸は5段階、エレベーションは必要最小限のレベルに絞る。
- 階層は大きさと余白の比例で示す: 重要な要素・上位見出しほど大きなサイズと余白を与え、関連の強い要素同士は近づける。
- 業務システム・管理画面では情報量を優先した密度（Dense テキスト、行高120〜130%、エレベーションの高低差を狭く）が許容される一方、読み物では可読性（行高150%以上、行長全角40文字程度）を優先する。
- 本文・UIは16 CSS px以上が基準で、14 CSS pxは例外、14 CSS px未満は原則不可とする。
- リキッドレイアウト・レスポンシブで、拡大縮小やフォント変更に耐える構造にする（ブレークポイントは1つ、768pxが例）。
- 視覚的な順序と DOM（読み上げ・フォーカス）順序を一致させる。
- 初期値は編集の起点であり、ブランドに合わせて変えてよいが、セマンティックカラーの色相と意味、フォーカスインジケーターは変えてはならない。
- コンポーネントはプリミティブな部品として提供され、サービス側でラベル入りコンポーネントや組み合わせセットを定義して文言と構成の揺れを防ぐ。
