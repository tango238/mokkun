# v2 YAML 生成ルール（DADS の UX 指針に基づく）

mokkun v2 フォーマット（`02-schema-v2.md`）で画面モックを **生成する側**（人でも LLM でも）が守るルール。
根拠はデジタル庁デザインシステム（DADS）β版 v2 の公式文書で、出典は `reference/` の抽出ノートに対応する。
各ルールには ID を振る。`[必須]` は違反するとモックとして成立しないもの、`[推奨]` はよほどの理由がなければ守るもの。

出典の略記: `C:<component>` は `reference/dads-components-ux.md` の該当コンポーネント、
`F:<section>` は `reference/dads-foundations-ux.md` の該当セクション。

---

## 0. 生成の手順

YAML は上の層から順に決める。下の層を先に書くと部品の列挙になり、旧 TeamKit 形式と同じ失敗をする。

1. **Flow を決める。** 業務成果（outcome）を一文で書き、画面の順序に分ける。入力→確認→完了が基本形（R-F01）。
2. **View を決める。** 画面ごとにゴールを一文で書く。1画面の主アクションは1つ（R-V01）。
3. **Section を決める。** ゴールに至る小タスクに分け、動詞＋名詞で名付ける。関連の強い項目は同じ Section に置く。
4. **Field を決める。** 項目ごとに「何を聞くか」を決めてから、選択肢の数と性質で component を選ぶ（§4 の表）。
5. **文言を書く。** ラベル、サポートテキスト（help / format / example / whyRequired）、ボタンラベル、エラー文を §6 の規則で書く。
6. **自己点検。** §7 のチェックリストを通す。

## 1. App 層のルール

| ID | ルール | YAML での表現 | 出典 |
|---|---|---|---|
| R-A01 [必須] | グローバルナビの項目ラベルは遷移先の画面名そのものにする。「詳細」「その他」のような抽象語を使わない | `navigation[].items[].label` は省略して view の title を使う | C:水平メニュー |
| R-A02 [推奨] | メニューの階層は group → view の2段までにし、3段以上作らない | `navigation` は group と items の2段のみ | C:モバイルメニュー, C:水平メニュー |
| R-A03 [推奨] | 項目数が多いときは group で整理する。1つの group に view を詰め込みすぎない | group を目的別に分ける | C:水平メニュー |
| R-A04 [必須] | 全画面共通の通知は、常設・長期の重要情報に限る。処理完了やステータス変化は通知に使わない | `app.notifications` はメンテナンス予告など。処理結果は View の `states` に書く | C:ノティフィケーションバナー |
| R-A05 [推奨] | 通知のタイトルは内容が一目で分かる具体的な文にする（「お知らせ」ではなく「11月10日 2:00-4:00 にメンテナンスを実施します」） | `notifications[].message` | C:ノティフィケーションバナー, C:緊急時バナー |
| R-A06 [推奨] | 閉じられる通知にするのは、閉じた状態を記憶でき再表示の手段がある場合だけ | `dismissible: true` は乱用しない | C:ノティフィケーションバナー |
| R-A07 [推奨] | ヘッダーにはシステム名・利用者名・テナントなど、どの画面でも必要な情報だけを置く | `app.header` | C:ヘッダーコンテナ, C:ユーティリティリンク |

## 2. Flow 層のルール

| ID | ルール | YAML での表現 | 出典 |
|---|---|---|---|
| R-F01 [必須] | 複数画面にまたがる手続きは、論理的なステップに分けて提示する。入力→確認→完了が基本形 | `flows.<name>.steps` に view を順に並べる | C:ステップナビゲーション |
| R-F02 [必須] | ステップ名は中身が分かる具体名にする（「基本情報入力」「本人確認」）。「ステップ1」のような番号だけにしない | `steps[].label` | C:ステップナビゲーション |
| R-F03 [推奨] | 自動変換や正規化した入力値は確認画面で見せ、ユーザーが承認または修正できるようにする | 確認 View を `kind: readonly` の Section で作り、「入力に戻る」を副アクションに置く | C:インプットテキスト |
| R-F04 [必須] | 完了やステータス変化はモーダルで知らせない。完了画面か成功バナーで伝える | 完了 View に `states.success` を書く | C:モーダルダイアログ, C:ノティフィケーションバナー |
| R-F05 [必須] | 確認ダイアログ（`confirm`）は、取り消せない操作の押し間違い防止に限って使う。確認画面の直後の確定ボタンに重ねない | `confirm` は削除・破棄・取消など。danger な操作には `danger: true` | C:モーダルダイアログ |
| R-F06 [推奨] | 確認ダイアログだけを安全対策にしない。取り消し・復元できる設計を先に検討する | 削除後に「元に戻す」導線を置けるなら `confirm` を省く | C:モーダルダイアログ |
| R-F07 [推奨] | 途中保存できる長い手続きは `resumable: true` とし、各入力画面に「下書き保存」を副アクションとして置く | `resumable`, `secondaryActions` | C:ステップナビゲーション（手続きの俯瞰） |
| R-F08 [推奨] | 一時的な処理待ちはステップではなくローディング状態で表す | `states.loading` | C:プログレスインジケーター |

## 3. View 層のルール

| ID | ルール | YAML での表現 | 出典 |
|---|---|---|---|
| R-V01 [必須] | 主アクション（塗りボタン）は1画面に1つ。最も重要なアクションだけを主にする | `primaryAction` は1つ（スキーマが強制） | C:ボタン |
| R-V02 [必須] | 副アクション（アウトライン）は同時に原則3つまで。4つ以上になるならフローを見直す | `secondaryActions` は3件以内 | C:ボタン |
| R-V03 [必須] | キャンセル・中止・戻るは tertiary（テキストボタン）で、1画面に1つまで | `secondaryActions[].style: tertiary`（`kind: navigate` で戻り先へ） | C:ボタン |
| R-V04 [推奨] | 進む操作（次へ・確定）は右、戻る・キャンセルは左に置く。配置は YAML ではなく描画側が担うので、生成側は style を正しく付けるだけでよい | `style` を正しく付ける | C:ボタン |
| R-V05 [必須] | ボタンを無効化しない。押せない理由があるなら、押下時にエラーで何をすべきか案内する | `disabled` 相当のキーを使わない。`states.error` に案内文を書く | C:ボタン |
| R-V06 [必須] | ボタンにはテキストラベルを必ず付ける。アイコンだけにしない | `label` は必須 | C:ボタン, F:色とアイコン |
| R-V07 [必須] | 画面タイトル（h1）はページの主題。ゴールは別に `goal` として書き、タイトルに混ぜない | `title`, `goal` | C:見出し |
| R-V08 [推奨] | 画面の説明は、ユーザーがこれから何をするかを1〜2文で書く。読まなくても進める補足は Section の note に回す | `description` | C:注釈ブロック |
| R-V09 [必須] | エラー状態のメッセージは「何が起きたか」と「どこを見ればよいか」を書く。「入力に誤りがあります」だけにしない | `states.error.message` | C:インプットテキスト, C:ノティフィケーションバナー |
| R-V10 [推奨] | 成功メッセージは何が完了したかを具体的に書く（「受注 #10234 を登録しました」） | `states.success.message` | C:ノティフィケーションバナー |
| R-V11 [推奨] | タブは「同じ主題の異なる観点」を切り替えるときだけ使う。絞り込みや手続きの進行にタブを使わない | `layout: tabs` は概要／仕様／履歴のような観点切替に限る | C:タブ |
| R-V12 [推奨] | Section が多く長い画面では目次を付ける | `layout: sectioned` | C:目次 |
| R-V13 [推奨] | 一覧画面は「絞り込む」Section と「選ぶ」Section（kind: list）の2つを基本形にし、新規作成を主アクションにする | 例: `filter` + `results` | C:テーブルコントロール |

## 4. Section 層のルール

| ID | ルール | YAML での表現 | 出典 |
|---|---|---|---|
| R-S01 [必須] | Section の見出しは中身の主題を表す。見出しレベルは描画側が h2 に固定するので、YAML で階層を作らない | `title` | C:見出し |
| R-S02 [推奨] | 関連の強い項目を同じ Section にまとめ、関連の弱い項目は分ける。1 Section の項目は目安 7 個以内 | `fields` | F:余白（関係性の明示） |
| R-S03 [必須] | 重要な情報や入力必須の項目を折りたたまない。折りたたみは「読まなくても手続きを進められる補足」や「詳細オプション」に限る | `reveal: collapsed` は任意項目だけの Section に限る | C:アコーディオン, C:ディスクロージャー, C:注釈ブロック |
| R-S04 [必須] | 折りたたむ Section の title は中身を要約した名詞句にする。「詳細を見る」「もっと見る」のような動作だけの表現にしない | `title` | C:ディスクロージャー |
| R-S05 [推奨] | 表示領域を小さくするためだけに折りたたまない | `reveal` の濫用禁止 | C:アコーディオン |
| R-S06 [必須] | 名前と値のペアを見せる画面（確認画面、詳細画面）は `kind: readonly`（説明リスト）で作り、入力欄の readonly で代用しない | `kind: readonly` + `fields[].value` | C:説明リスト, C:インプットテキスト |
| R-S07 [必須] | 行と列で比較・一覧するデータは `kind: list`（テーブル）。名前と値のペアにはテーブルを使わない | `kind: list` | C:テーブル |
| R-S08 [推奨] | テーブルの列は1行1レコードで、入れ子や結合を避ける。並び替えできる列だけ `sortable: true` | `list.columns` | C:テーブル |
| R-S09 [推奨] | 一覧の絞り込みはキーワード検索と少数の条件に留め、複雑な検索は別 Section にする | `list.search`, 絞り込み Section | C:テーブルコントロール, C:検索ボックス |
| R-S10 [推奨] | 一覧に 0 件のときの文言を必ず書く | `list.empty` | C:テーブル（図例）, C:ページナビゲーション |
| R-S11 [推奨] | 繰り返し入力（明細など）は `repeatable` にし、追加ボタンのラベルに対象を入れる（「明細を追加」） | `repeatable.addLabel` | C:ボタン（ラベルの具体性） |
| R-S12 [推奨] | Section の note は「読まなくても進める補足」に限り、入力条件や制約は Field の help / format に書く | `note` vs `help` | C:注釈ブロック |
| R-S13 [推奨] | 項目は縦に積む。横に並べるのは郵便番号＋住所、年＋月＋日のように一組で読む項目だけ | `columns` は 1 を基本とし、2〜3 は一組の項目に限る | C:インプットテキスト（整列） |

## 5. Field 層のルール

### 5.1 component の選び方

| 聞きたいこと | 条件 | component | 出典 |
|---|---|---|---|
| 1行の文字 | | `text` | C:インプットテキスト |
| 数値 | | `number` | C:インプットテキスト |
| 自由記述 | まず質問を分割できないか検討する | `textarea` | C:テキストエリア |
| 1つを選ぶ | 選択肢 5 個以下 | `radio` | C:セレクトボックス, C:ラジオボタン |
| 1つを選ぶ | 選択肢 6 個以上 | `select` | C:セレクトボックス |
| 1つを選ぶ | 選択肢が多く文字で絞り込みたい | `combobox` | C:コンボボックス |
| 複数を選ぶ | | `checkbox` + `multiple: true`（`select` + `multiple` は使わない） | C:チェックボックス |
| はい／いいえ | 保存・送信で確定する | `checkbox` | C:チェックボックス, C:スイッチ |
| オン／オフ | 切り替えた瞬間に反映され、その場で結果が見える | `toggle` | C:スイッチ |
| 日付 | 既知の日付（生年月日、有効期限） | `date`（`inline` なし） | C:日付ピッカー |
| 日付 | 近い期間から曜日を見て選ぶ（予約日、希望日） | `date` + `props.calendar: true` | C:日付ピッカー |
| 時刻 | | `time` | — |
| ファイル | | `file`（画像は `accept: image`） | C:ファイルアップロード |
| 状態・分類の表示 | | `status` / `badge` / `chip` + `value` | C:チップラベル |

### 5.2 項目のルール

| ID | ルール | YAML での表現 | 出典 |
|---|---|---|---|
| R-I01 [必須] | すべての項目にラベルを付ける。ラベルは項目を端的に表す名詞 | `label` | C:インプットテキスト, C:テキストエリア |
| R-I02 [必須] | 必須・任意を項目ごとに明示する。描画側が「※必須」「※任意」を付けるので、`required` を正しく付ける | `required` | C:インプットテキスト, C:日付ピッカー |
| R-I03 [推奨] | 必須にする理由が自明でない項目は理由を書く | `whyRequired` | C:インプットテキスト（サポートテキスト） |
| R-I04 [必須] | 入力形式の条件と例はサポートテキストに書く。placeholder は使わない（スキーマに placeholder はなく、`example` はサポートテキストに描画される） | `format`, `example`, `help` | C:インプットテキスト, C:日付ピッカー |
| R-I05 [推奨] | 入力できる文字種を限定しない。全角・ハイフン有無などは受け入れて正規化する前提で、format には「全角でも可」のように書く | `format` | C:インプットテキスト, C:日付ピッカー |
| R-I06 [必須] | 文字数制限があるときは上限をラベルかサポートテキストに書く。エラーで初めて上限が分かる状態にしない | `label` または `help` に「100文字以内」 | C:テキストエリア |
| R-I07 [必須] | 選択肢ラベルは具体的に。任意のラジオには「あてはまるものはない」のような無選択の選択肢を加える | `options` | C:ラジオボタン |
| R-I08 [必須] | `readonly` の入力欄は原則使わない。編集できない値は `kind: readonly` の Section か表示系 component で見せる | `readonly` を避ける | C:インプットテキスト |
| R-I09 [推奨] | やむを得ず `readonly` にするのは、同じ行に編集可能な項目と自動入力の項目が並ぶ場合などに限り、help に編集できない理由を書く | `readonly: true` + `help: "商品を選ぶと自動で入ります"` | C:インプットテキスト |
| R-I10 [必須] | メールアドレスを `@` の前後で分けない。電話番号・郵便番号も原則1つの項目にする | 1 Field | C:インプットテキスト |
| R-I11 [推奨] | 年月日は3分割の入力欄として描画されるので、日付はサポートテキストに「西暦で」と入力例を書く | `help: "西暦で入力してください。例）2026年11月14日"` | C:日付ピッカー |
| R-I12 [推奨] | 表示系（status / badge / chip）は色だけに頼らず、`value` に状態の名前を必ず入れる | `value: "審査中"` | C:チップラベル |
| R-I13 [推奨] | 条件表示（`visibleWhen`）は、参照先の項目より後ろに置き、条件が変わることを参照先の help で予告する | `visibleWhen` | C:インプットテキスト（予測できない変化） |
| R-I14 [推奨] | 項目ごとのエラー文は「＊」で始め、何をどう直すかを書く（「＊氏名をカタカナで入力してください」） | `props.error` | C:インプットテキスト |
| R-I15 [推奨] | 入力欄の幅は内容に見合わせる（郵便番号は短く、住所は長く）。すべて同じ幅にしない | `width: xs / sm / md / lg / full` | C:インプットテキスト（横幅） |

## 6. 文言のルール

| ID | ルール | 出典 |
|---|---|---|
| R-W01 [必須] | ボタンは動詞で終える具体名（「確認へ進む」「確定する」「明細を追加」）。「OK」「送信」だけで済ませない | C:ボタン |
| R-W02 [必須] | 同じ意味のボタンは全画面で同じ文言にする（「戻る」「キャンセル」「保存」を揺らさない） | F:リンクテキストと文言 |
| R-W03 [必須] | リンクや遷移のラベルは行き先が分かる文にする。「こちら」「詳細」を単独で使わない | F:リンクテキストと文言, C:水平メニュー |
| R-W04 [必須] | エラー文は具体的に。「入力に誤りがあります」「正しく入力してください」を使わない | C:インプットテキスト |
| R-W05 [推奨] | サポートテキストは1〜2文、全角 40 文字程度まで。長い補足は Section の note へ | F:タイポグラフィ（行長） |
| R-W06 [推奨] | 通知・バナーのタイトルは内容そのもの（「登録期間が延長されました」）。「お知らせ」「重要」だけにしない | C:ノティフィケーションバナー, C:緊急時バナー |
| R-W07 [推奨] | 見出しと目次・ナビのラベルは同じ文言にする | C:目次 |
| R-W08 [推奨] | 敬体で統一し、ユーザーへの依頼は「〜してください」、システムの状態は「〜しました」で書く | （本プロジェクトの規約） |

## 7. 生成後のチェックリスト

- [ ] 各 Flow に outcome があり、steps が入力→確認→完了の形か（R-F01）
- [ ] 各 View の primaryAction が1つ、secondaryActions が3つ以内、tertiary が1つ以内か（R-V01〜03）
- [ ] 確認画面の直後の確定ボタンに `confirm` を重ねていないか（R-F05）
- [ ] 折りたたんだ Section に必須項目がないか（R-S03）
- [ ] 確認・詳細画面が `kind: readonly` で、入力欄の readonly で代用していないか（R-S06, R-I08）
- [ ] 選択肢 5 個以下が radio、6 個以上が select、複数選択が checkbox か（§5.1）
- [ ] toggle を使っている項目は、切り替えた瞬間に反映されるものか（§5.1）
- [ ] 全項目に label と required の明示があるか（R-I01, R-I02）
- [ ] 入力条件・例が help / format / example にあり、placeholder 的な書き方になっていないか（R-I04）
- [ ] 文字数制限がある項目で上限を事前に示しているか（R-I06）
- [ ] エラー文と通知文が具体的か（R-V09, R-W04, R-W06）
- [ ] ナビのラベルが画面名と一致し、抽象語がないか（R-A01）
- [ ] 一覧に `empty` があるか（R-S10）

## 8. サンプル `examples/v2/order-entry.yaml` への適用

このルールで見直した結果、サンプルは次を修正する（修正は実装側の作業として記録）。

| 箇所 | 違反 | 修正 |
|---|---|---|
| settings の `emailNotify`（toggle）に「保存」主アクション | 確定操作を伴う項目にスイッチを使わない（§5.1） | `checkbox` にする |
| order_confirm の「確定する」に `confirm` | 確認画面の直後に確認ダイアログを重ねない（R-F05） | `confirm` を外す |
| order_form の「やめる」が secondary | 中止は tertiary（R-V03） | `style: tertiary` |
| lines の `unitPrice` が readonly で理由なし | readonly は理由を help に書く（R-I09） | `help` を追加 |
| 顧客名の combobox（選択肢 2 個） | 少数の選択肢は radio（§5.1） | サンプルでは候補が多い前提として options を増やす |
| 配達希望日に入力例なし | 日付はサポートテキストに入力例（R-I11） | `help` に例を追加 |

## 9. スキーマへの反映が必要な点

ルールを表現するために v2 スキーマに次を追加する（`02-schema-v2.md` にも反映する）。

- `Action.style` に `tertiary`（テキストボタン）を追加。旧レンダラーへは secondary として変換。
- `Field.width`（`xs` / `sm` / `md` / `lg` / `full`）を追加。旧レンダラーでは無視。
- `date` の `props.calendar: true` でカレンダーボタンを付ける（`inline: true` は月表示のまま）。
